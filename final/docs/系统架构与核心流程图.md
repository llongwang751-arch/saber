### 架构结论

- 页面只是入口，核心在 FastAPI、多用户 Agent、RAG、记忆、工具编排、业务服务和评测闭环；
- 默认本地模式已经持久化，不是重启即丢的纯内存 Mock；
- PostgreSQL、Milvus、Elasticsearch、Neo4j、Kafka 是增强项，不是启动前置条件；
- 评测数据单独按用户落到 `runtime/evaluation-tenants/`，防止 Dataset、Trace、Badcase 串号。

## 2. 核心对话流程时序图

```mermaid
sequenceDiagram
    autonumber
    actor U as 用户
    participant V as Vue / Pinia
    participant F as FastAPI Middleware
    participant R as AgentRegistry
    participant A as UnifiedAgent
    participant M as STM / LTM / Preference
    participant DB as SQLite 或 PostgreSQL
    participant RT as Router
    participant X as Agentic RAG / RAG / ReAct
    participant L as LLM / Embedding API

    U->>V: 输入消息、选择知识库或 Skill
    V->>F: POST /api/chat/stream + Bearer JWT
    F->>F: 校验 JWT、请求大小、Request ID、超时
    F->>R: 根据 user_id 获取专属 Agent
    R-->>F: UnifiedAgent(user_id)
    F->>A: process_stream(query, options)

    rect rgb(246,248,252)
        Note over A,M: Prepare
        A->>M: STM.add(user, query)
        A->>DB: 保存 user chat_history
        A->>M: 规则提取偏好并立即保存
        A-->>M: AsyncMemoryWriter 异步做 LLM 偏好提取与 LTM.add
        A->>RT: 根据 use_rag / RAG loaded / 报告关键词路由
        RT-->>A: rag_agent / rag / react
        A->>M: ContextAssembler 读取偏好 + LTM + STM 等槽位
    end

    A-->>V: SSE route / memory

    alt rag_agent
        A->>X: research → writer → review → doc 固定 DAG
        X-->>A: 报告、Review 元数据与文档对象
    else rag
        A->>X: RAGEngine.query_with_history
        X->>L: 可选 query rewrite / rerank / answer compose
        L-->>X: 基于检索上下文的回答
        X-->>A: answer + search_results
    else react
        A->>L: Planner 生成 TaskGraph
        L-->>A: 节点、依赖、工具参数
        A->>X: GraphRuntime 拓扑分层执行
        X->>X: 直接回答或工具；parallel / race / retry / cancel / snapshot
        X-->>A: observations
        A->>L: 汇总 observations 生成答案
    end

    A-->>V: SSE step / tool_call / rag_result / token

    rect rgb(252,247,249)
        Note over A,DB: Finalize
        A->>M: STM.add(assistant, answer)
        A->>DB: 保存 assistant chat_history
        A-->>M: 异步从回复提取长期记忆
        A-->>M: 达阈值后去重、合并、衰减、淘汰
        M-->>DB: 权威行 + memory_outbox 同事务提交
        A-->>DB: 每 N 轮保存 Task Snapshot
    end

    A-->>V: SSE done
    V-->>U: 展示答案、步骤、引用和完成状态
```

当前主循环是 `_prepare → _dispatch_mode → _finalize`。取消、流式事件、任务快照和异步记忆写入都在这条链上。

## 3. RAG 三路混合检索流程图

```mermaid
sequenceDiagram
    autonumber
    actor U as 用户
    participant A as UnifiedAgent
    participant R as RAGEngine
    participant RW as Query Rewriter 可选
    participant H as HybridStore
    participant E as Embedding API
    participant M as Milvus
    participant S as Elasticsearch
    participant G as Neo4j KG
    participant P as PostgreSQL / LocalRagChunkRepo
    participant RR as RRF + Reranker
    participant L as LLM

    U->>A: 开启知识库后提问
    A->>R: query_with_history(question, STM history)
    R->>RW: 可选：改写成 1～N 个查询
    RW-->>R: queries

    loop 每个 query，可并行
        R->>H: search(query, candidate_pool)

        alt Milvus 与 ES 都可用：hybrid
            par 语义路
                H->>E: embed(query)
                E-->>H: query vector
                H->>M: vector search
                M-->>H: pg_id rank list
            and 关键词路
                H->>S: BM25 search
                S-->>H: pg_id rank list
            and 图谱路
                H->>G: entity / relation traversal
                G-->>H: pg_id rank list
            end
            H->>RR: 按 rank 做三路 RRF
            Note over RR: semantic = w/(k+rank)<br/>keyword = (1-w)/(k+rank)<br/>KG = 1/(k+rank)
            RR->>P: 按融合后的 pg_id 回表取 child + parent
            P-->>RR: 可引用原文
        else 只有 Milvus
            H->>E: embed(query)
            H->>M: semantic search
            M-->>H: semantic results
        else 只有 ES
            H->>S: BM25 search
            S-->>H: keyword results
        else 外部检索均不可用
            H->>P: search_local(query, user_id)
            P-->>H: SQLite 中英文词法余弦结果
        end
    end

    H->>RR: 多 query 再做一次 RRF，随后可选 LLM rerank
    RR-->>R: top-k HybridResult
    R->>R: parent 优先、按内容去重、拼接 context
    R->>L: 仅根据 context 回答，禁止编造
    L-->>R: answer
    R-->>A: answer + source + score
    A-->>U: 回答与检索证据
```

### 入库链路

```mermaid
flowchart LR
    Upload[TXT / Markdown / 可提取文字 PDF] --> Parser[Document Parser]
    Parser --> Parent[Parent Splitter]
    Parent --> Child[Child Splitter + overlap]
    Child --> Embed[逐块 Embedding<br/>失败允许降级]
    Child --> Truth[(PostgreSQL 或 Local SQLite<br/>保存 child / parent / doc / version / user)]
    Embed --> Milvus[(Milvus)]
    Child --> ES[(Elasticsearch)]
    Child -->|后台 best effort| KG[(Neo4j KG)]
    Truth --> Loaded[RAG loaded = true]
```

需要准确表述：**三路融合只在 Milvus 与 Elasticsearch 都连通时进入 `hybrid` 模式**，Neo4j 可用时成为第三路；任一主检索基础设施不可用会降级为单路，二者都不可用时走本地 SQLite 词法检索。

## 4. 记忆系统详细流程图

```mermaid
flowchart TB
    subgraph Startup[每个用户 Agent 冷启动]
        Login[JWT 得到 user_id] --> Registry[AgentRegistry 懒创建]
        Registry --> Parallel{4 路并发 bootstrap}
        Parallel --> RestorePref[恢复 Preference]
        Parallel --> RestoreLTM[恢复 LongTerm Memory]
        Parallel --> RestoreChat[恢复 Chat History / Snapshot]
        Parallel --> RestoreRAG[恢复 RAG Chunks]
        Registry --> KGInit[恢复完成后初始化 KG / GraphMemory]
    end

    subgraph ReadPath[每轮读取]
        Query[用户消息] --> STMWrite[写 ShortTerm 滑动窗口]
        STMWrite --> ChatPersist[持久化 chat_history]
        Query --> RulePref[同步规则提取 Preference]
        Query --> Recall{LTM Recall}
        Recall -->|Embedding 可用| Vector[Cosine Similarity]
        Recall -->|Embedding 失败| TF[TF 词袋余弦]
        Vector --> Score[score = similarity × 0.7 + importance × 0.3]
        TF --> Score
        Score --> Filter[只取 active、阈值与 top-k]
        Filter --> Prefix[Preference + 相关记忆 + STM history]
        Prefix --> LLMCall[注入 Chat / Tool / ReAct / RAG]
    end

    subgraph WritePath[每轮写入]
        Query --> AsyncUser[AsyncMemoryWriter]
        AsyncUser --> LLMPref[LLM 提取 Preference]
        AsyncUser --> LTMAdd[LTM.add 用户消息]
        Answer[Assistant 回答] --> STMAnswer[写 STM]
        Answer --> ChatAnswer[持久化 chat_history]
        Answer --> AsyncAnswer[异步抽取长期事实]
        AsyncAnswer --> LTMAdd2[LTM.add 回复事实]
        LTMAdd --> Durable[(SQLite / PostgreSQL)]
        LTMAdd2 --> Durable
        LLMPref --> Durable
        Durable --> Outbox[(memory_outbox)]
        Outbox --> Worker[SQLite 本地 Worker / PostgreSQL 生产 Supervisor]
        Worker --> LocalLedger[SQLite 本地投影账本]
        Worker -.仅生产 PostgreSQL.-> VectorProjection[Milvus 记忆向量]
        Worker -.仅生产 PostgreSQL.-> GraphWrite[Neo4j 记忆节点与关系]
    end

    subgraph Consolidation[达到 trigger_interval 后]
        Trigger[need_consolidation] --> Decay[按天衰减 importance]
        Decay --> Dedup[相似度 ≥ dedup：去重]
        Dedup --> Merge[相似度 ≥ merge：合并并记录 superseded_by]
        Merge --> Expire[TTL + 最低重要性：淘汰]
        Expire --> GraphProtect[Graph 可用时保护高中心度节点并同步关系]
        GraphProtect --> SyncDB[事务同步状态 / 删除 / 更新 + Outbox]
    end

    Startup --> ReadPath
    ReadPath --> WritePath
    WritePath --> Consolidation
```

### 当前图记忆边界

- 已进入主链路：长期记忆权威行与 Outbox 同事务提交，投影 Worker 按版本/哈希幂等执行；SQLite 更新本地账本，生产 PostgreSQL 的 Outbox 才按 Milvus/Neo4j target 拆分；
- 已有实现但当前主对话未调用：`MemoryManager.recall()` 的种子召回 + Neo4j 1-hop 扩展；
- 当前主 dispatch 通过 `_build_context_prefix()` 使用 `ContextAssembler`，装配异常时才回退 `_build_memory_system_prefix()`；
- PostgreSQL 生产消费者具备租约、指数退避、dead-letter 与周期 reconcile，但真实 Milvus/Neo4j 的断线、乱序与并发恢复仍需完整环境故障注入。

## 6. 与截图中的 Go 版对照

| 截图中的 Go 版 | 当前 Python 版 |
|---|---|
| `config.go` | `config/config.py` |
| `main.go` | `final/main.py` |
| `go.mod` | `requirements.txt` |
| `frontend/index.html` 单文件前端 | `web/src` Vue 3 + Pinia；旧 HTML 仅 fallback |
| `internal/agent` | 保留，并增加 GraphRuntime、SubAgent、Cancel、Registry |
| `internal/infra` | 保留，并拆出 `platform/` 与 `repo/` |
| 没有业务应用层 | 增加 `application/`：认证、Skill、养殖、本地持久化 |
| 没有质量评测层 | 增加 `evaluation/`：评测、策略、实验 API 与完整闭环；数量以 OpenAPI 为准 |
| 主要依赖 PG 持久化 | 增加本地 SQLite 真相源，外部基础设施可选增强 |
| 无数据库迁移目录 | 增加 Alembic 0001～0016 版本链 |

所以答案是：**目录结构和语言运行时不同，但 Go 基准链路已经完成行为级、协议级和失败语义级复刻；Python 版在此基础上扩展为“Agent 平台 + 本地持久化 + 业务场景 + 质量评测工作台”。** 逐项源码映射见 `Go-Python完全复刻对照与面试说明.md`。
