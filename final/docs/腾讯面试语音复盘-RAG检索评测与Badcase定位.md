## 2. 项目中的 RAG 完整链路

```text
文档上传
  ↓
解析、清洗
  ↓
父段落切分
  ↓
父段落继续切成子块
  ↓
对子块生成 Embedding，并建立关键词索引
  ↓
保存子块、父段落内容、文档信息等元数据
  ↓
用户查询与可选 Query Rewrite
  ↓
向量召回 + BM25 召回 + 可选图检索
  ↓
RRF 融合候选结果
  ↓
可选 Rerank 精排
  ↓
根据父段落补全上下文、去重、控制 Token 预算
  ↓
LLM 根据证据生成答案与引用
```

源码入口：

- `internal/rag/rag.py::Engine.ingest()`：父段落、子块切分与入库；
- `internal/rag/rag.py::Engine.query_with_history()`：带历史消息的查询流程；
- `internal/rag/hybrid.py`：多路检索、RRF 融合和候选组装；
- `internal/rag/reranker.py`：LLM 重排及失败回退；
- `internal/repo/ragchunk.py`：子块与 `parent_content` 的持久化。

### 当前实现边界

当前 Python 代码会让每个子块保存一份对应的 `parent_content`。它能够完成“小块检索、父段落回填”，但不是最理想的规范化数据模型。

生产级改进可以是：

```text
parent_segments
  - parent_id
  - document_id
  - content
  - start_offset
  - end_offset

child_chunks
  - child_id
  - parent_id
  - content
  - start_offset
  - end_offset
  - embedding
```

这样可以减少父段落重复存储，并能按照 `parent_id` 稳定去重、更新和合并相邻段落。

## 3. 高频题一：为什么使用小块召回、父段落补全

### 3.1 面试官真正想听什么

面试官不是只想听“为了提高准确率”，而是希望候选人讲清楚：

1. 大块检索有什么问题；
2. 小块解决了什么问题；
3. 小块又引入了什么新问题；
4. 父段落补全如何弥补；
5. 方案有什么工程代价。

### 3.2 标准回答

> 大段落通常包含多个主题，生成一个向量后语义会被稀释，容易把无关信息一起召回。项目先把父段落切成语义更集中的子块，主要对子块建立向量和关键词索引，从而提高细粒度命中能力。但只把子块交给模型会切断上下文，所以命中子块后，再根据父子关系回填完整父段落，并做去重和 Token 预算控制。这个方案在检索精度与上下文完整性之间做平衡，代价是索引数量增加，也需要维护父子关系和去重逻辑。

### 3.3 本次回答评价

回答方向正确，已经说出了：

- 大段落无关信息多；
- 小块更容易检索；
- 命中子块后补回父段落。

还应主动补充：

- 大块不仅“信息多”，还会产生多主题语义稀释；
- 只用小块会丢失上下文；
- 返回父段落前需要去重和长度控制；
- 当前实现保存的是 `parent_content`，不是独立 `parent_id` 表。

### 3.4 可能追问

**追问：为什么不直接对父段落做向量检索？**

> 父段落可能同时包含多个语义主题，查询只对应其中一句时，整体向量容易稀释这个局部信号。小块主题更集中，更容易在第一阶段命中。

**追问：小块越小越好吗？**

> 不是。过小会丢失语义完整性、增加块数量和索引成本，还会让同一父段落的多个碎片重复召回。块大小和 overlap 应通过验证集按 Recall@K、排序指标、延迟及 Token 成本共同选择。

**追问：代码块怎么切？**

> 应优先按语言结构或 fenced code block 保持函数、类等语义单元完整，不能机械地从函数中间截断。Markdown 文档则优先保留标题层级，再对超长章节递归切分。

## 4. 高频题二：为什么不能只用向量检索

### 4.1 两类检索的分工

| 检索方式 | 擅长 | 弱点 |
|---|---|---|
| 向量检索 | 语义相似、同义表达、自然语言改写 | 精确编号、版本号、错误码、API 名称可能漏召回；也可能语义漂移 |
| BM25 | 专有名词、关键词、编号、错误码、接口路径等字面匹配 | 对同义词和语义改写不敏感 |

例如用户问：

```text
远程重排连续失败三次后怎么处理？
```

BM25 能抓住“远程重排”“三次失败”等精确信号；向量检索能够召回“连续异常后进入冷却和降级”的同义描述。二者互补通常比单路检索稳健。

### 4.2 标准回答

> 向量检索擅长语义相似和同义改写，但对错误码、版本号、API 名称、专有名词等精确信号不稳定，也可能召回语义相近但事实不匹配的内容。BM25 根据词频和逆文档频率做字面匹配，正好补足这些精确信号。因此项目使用向量和 BM25 进行混合召回，再通过 RRF 融合排名，用 Rerank 做精排。

### 4.3 本次回答评价

这部分已经能够正确表达：

- BM25 负责关键词匹配；
- 向量检索负责语义相似；
- 语义相似不代表事实或关键词一定匹配；
- 两路召回应互补。

面试时不要说“BM25 可以直接精确找到正确文档”，因为 BM25 也只是相关性检索，不保证返回结果一定正确。

## 5. 高频题三：为什么使用 RRF，不直接相加原始分数

### 5.1 RRF 公式

RRF 全称是 Reciprocal Rank Fusion，倒数排名融合：

```text
RRF(d) = Σ_i w_i / (k + rank_i(d))
```

其中：

- `d`：候选文档；
- `rank_i(d)`：文档在第 i 路检索中的名次；
- `w_i`：该检索通道的权重；
- `k`：平滑常数，控制不同名次之间的衰减程度。

当前代码在 `internal/rag/hybrid.py` 中使用 RRF；默认常数的兜底值为 60。具体通道权重应以实际运行配置为准，不要死背历史简历里的数字。

### 5.2 为什么不直接加分

Milvus 余弦相似度、BM25 分数和图检索分数：

- 取值范围不同；
- 统计分布不同；
- 不同查询之间也可能不可比。

直接相加需要稳定的归一化和校准。RRF 只使用名次，因此在没有足够训练数据时更容易得到稳健的工程基线。

### 5.3 标准回答

> 向量相似度、BM25 和图检索分数不在同一量纲，直接相加需要做复杂且可能不稳定的归一化。RRF 只根据每一路的排名计算倒数排名分数，并按通道权重求和；多路共同命中的结果会自然上浮。它的优势是实现简单、对异构分数尺度稳健；缺点是丢失原始相似度强弱，救不回候选阶段完全漏掉的文档，而且 `k` 和权重仍需通过验证集调优。

### 5.4 不能夸大的地方

没有对比实验时，不能说“RRF 是最优方案”。更准确的表达是：

> RRF 是当前缺少学习排序训练数据时的稳健工程选择。要证明它优于线性加权，需要在固定评测集上比较 Recall@K、MRR、NDCG、延迟和参数敏感性。

## 6. 高频题四：为什么 RRF 后还需要 Rerank

### 6.1 两阶段架构

```text
向量召回 ─┐
           ├─ RRF 粗排融合 ─→ 候选池 ─→ Rerank 精排 ─→ Top K 上下文
BM25召回 ─┘
图检索  ──┘
```

RRF 的目标是低成本、高召回地构造候选集；Rerank 的目标是理解“问题—候选段落”的细粒度相关性并优化顺序。

### 6.2 标准回答

> RRF 主要依据各路名次做粗排，速度快但无法充分理解问题与文档之间的细粒度关系。Rerank 会把问题和少量候选文档一起比较，判断哪个候选真正能回答问题，因此能够提高 MRR 和 NDCG。不能一开始对全库做 Rerank，因为成本和延迟不可接受；也不能只用 RRF，因为排名融合仍可能把只有关键词重叠、实际不能回答问题的文档排在前面。

### 6.3 本次回答中的优秀比喻

可以用招聘流程解释：

- 简历库初筛：类似多路召回和 RRF 粗排，目标是不要漏掉潜在合适的人；
- 一面、二面：类似 Rerank 精排，用更高成本判断谁真正匹配；
- 最终进入模型上下文的 Top K：类似最后录用候选。

这个比喻适合帮助理解，但正式面试回答仍应使用“召回、候选集、排序精度、成本”这些术语收口。

### 6.4 当前代码事实

`internal/rag/reranker.py` 当前是 LLM 重排实现。若模型返回异常、JSON 无效或评分失败，会记录异常并回退到原 RRF 顺序。

这只能证明存在“单次失败回退”，不能直接说已经实现跨请求的 Closed/Open/Half-Open 三态熔断器。

## 7. RAG 离线评测集怎么设计

### 7.1 最小数据结构

每条离线用例至少需要：

```yaml
query: 用户问题
gold_document_ids: 正确文档集合
gold_chunk_ids: 正确证据块集合
gold_answer: 可选的参考答案
answerable: 是否可回答
relevance_labels: 可选，多级相关性标签
category: 事实型/专有名词/多跳/长文档/无答案等
```

Gold chunk 必须由人工标注或经过人工复核。不能让同一个待评测模型自己生成标准答案后再评自己，否则会形成自洽但不真实的评测闭环。

### 7.2 建议类别

评测集应覆盖：

- 事实型问答；
- 专有名词、错误码、版本号；
- 同义改写；
- 长文档局部信息；
- 多跳关系；
- 多轮指代；
- 不可回答问题；
- 冲突、过期和噪声文档；
- 工具失败或外部依赖异常。

### 7.3 避免数据泄漏

- 评测问题不能直接进入 Prompt 示例；
- 调参只使用验证集，最终指标只在独立测试集报告；
- 同一原文的改写问题应按文档或主题分组切分，避免一个版本进入验证集、另一个进入测试集；
- 模型或评测人员不可看到测试集答案后反复修改策略；
- 记录评测集版本、知识库版本、模型版本和配置版本。

## 8. Recall@K、MRR@K、NDCG@K

### 8.1 `@K` 的含义

`@K` 表示只观察检索结果的前 K 名。

- Recall@5：前 5 个结果召回了多少正确证据；
- MRR@10：前 10 个结果中第一个正确证据排在哪里；
- NDCG@10：前 10 名整体相关性排序质量如何。

### 8.2 Recall@K

```text
Recall@K = 前 K 名命中的正确证据数 / 所有正确证据数
```

回答的问题是：正确证据有没有进入候选集。

### 8.3 MRR@K

MRR 全称 Mean Reciprocal Rank，平均倒数排名。

某个问题的第一个正确结果：

- 排第 1：得分 1；
- 排第 2：得分 1/2；
- 排第 5：得分 1/5；
- 前 K 名没有出现：得分 0。

对全部问题取平均。它重点衡量第一个正确结果是否足够靠前。

### 8.4 NDCG@K

NDCG 同时考虑：

1. 文档是否完全相关、部分相关或不相关；
2. 高相关文档是否排在更靠前的位置。

如果只有二元“相关/不相关”标注，也能计算 NDCG；若具备多级相关性标注，它比 MRR 更能反映前 K 名的整体排序质量。

### 8.5 指标变化如何解释

如果加入 Rerank 后：

- NDCG、MRR 上升；
- Recall@10 基本不变；

这是合理现象。Rerank 只重新排列已经进入候选池的文档，不负责从全库新增召回，因此主要优化排序指标，而不是第一阶段召回率。

### 8.6 标准回答

> 我会人工标注查询对应的 gold chunk，固定离线评测集。第一阶段用 Recall@K 判断正确证据是否进入候选集，用 MRR@K 衡量第一个正确证据的位置；若有多级相关性标注，再用 NDCG@K 衡量前 K 名整体排序质量。然后分别对比纯向量、加入 BM25、使用 RRF 和加入 Rerank 后的指标变化，同时记录 P95 延迟和调用成本。

## 9. 无答案阈值怎么校准

### 9.1 问题本质

无答案阈值是在以下两类错误之间做权衡：

- 错误回答：知识库没有足够证据，系统却强行回答；
- 错误拒答：知识库存在充分证据，系统却说无法回答。

### 9.2 验证方法

准备同时包含 answerable 与 unanswerable 的独立验证集：

1. 运行完整检索、重排链路；
2. 收集每个问题最终相关性分数；
3. 遍历候选阈值；
4. 计算无答案识别的 Precision、Recall、F1；
5. 结合错误回答和错误拒答的业务成本选择阈值；
6. 在独立测试集进行一次最终确认。

### 9.3 阈值高低的影响

| 情况 | 常见后果 |
|---|---|
| 阈值过低 | 无证据问题也会被回答，幻觉和错误回答增加 |
| 阈值过高 | 有答案问题被大量拒答，可用性下降 |

### 9.4 用什么分数判断

优先考虑经过验证集校准的 Rerank 相关性分数，而不是 RRF 分数。

原因：

- RRF 是排名融合分数；
- 它受检索通道数量、排名和 `k` 影响；
- 它不具有稳定的概率含义；
- Rerank 直接评估问题和证据的相关性。

但 Rerank 分数也不能直接当概率，仍需校准。

### 9.5 不能夸大的地方

简历或旧文档中的 `0.30` 最多只能称为“当前工程初始值”。如果没有验证集上的 PR 曲线、F1 或业务成本实验，不能说它是最优阈值。

### 9.6 标准回答

> 无答案阈值本质是在错误回答和错误拒答之间做权衡，不能拍脑袋确定。我会构建同时包含可回答和不可回答问题的验证集，遍历阈值并观察 Precision、Recall、F1 以及两类错误的业务成本。阈值过低容易无依据回答，过高会过度拒答。最终优先使用校准后的 Rerank 分数，而不是 RRF 分数，因为 RRF 只是排名融合分数。

## 10. Precision、Recall、F1 手算

把“应该拒答的无答案问题”定义为正类。

```text
TP：正确识别并拒答的无答案问题
FP：本来有答案，却被错误拒答
FN：本来无答案，却被错误回答
TN：本来有答案，并且正常回答
```

公式：

```text
Precision = TP / (TP + FP)
Recall    = TP / (TP + FN)
F1        = 2 × Precision × Recall / (Precision + Recall)
```

记忆方法：

- Precision：我报出来的有多准；
- Recall：真正该抓的，我抓住了多少；
- F1：两者的调和平均。

### 本次计算题

已知：

- 实际无答案 20 个；
- 系统拒答 25 个；
- 正确拒答 15 个。

计算：

```text
Precision = 15 / 25 = 60%
Recall    = 15 / 20 = 75%
F1        = 2 × 0.60 × 0.75 / (0.60 + 0.75) ≈ 66.7%
```

本次回答虽然报出了 60% 和 75%，但解释时混用了上一题的数字。后续练习必须先写出 TP、FP、FN，再代公式，避免面试现场把分母说反。

## 11. Trace 如何定位 Badcase

### 11.1 场景

用户明确说“青霉素过敏”，Agent 却推荐了阿莫西林。

错误排查方式：

> 一看到答案错误，就断言是检索没有召回。

正确排查方式：

> 沿信息流检查每一层，找到“青霉素过敏”第一次丢失或被错误处理的位置。

### 11.2 排查顺序

```text
1. 原始输入
2. 意图识别与实体/槽位抽取
3. 短期记忆和多轮状态
4. Prompt 上下文组装
5. RAG 检索结果
6. 工具调用参数
7. 工具返回值
8. 最终模型输入
9. 模型输出
10. 安全规则与输出拦截
```

### 11.3 如何根据丢失点归因

| 第一次出现问题的位置 | 可能根因 |
|---|---|
| 原始请求中不存在 | 前端传输或会话拼接问题 |
| 输入存在，但实体抽取没有过敏信息 | 意图/槽位抽取问题 |
| 抽取成功，但后续 Prompt 没带上 | 状态管理或 Prompt 组装问题 |
| Prompt 中有过敏信息，但检索无禁忌证据 | 检索、索引或知识库覆盖问题 |
| 工具参数没携带过敏史 | 工具路由或参数构造问题 |
| 工具返回了禁忌，但模型仍推荐 | 生成约束或模型遵循问题 |
| 输出含危险建议且未拦截 | 安全规则或后处理问题 |

### 11.4 标准回答

> 我不会先假设是检索问题，而会沿 Agent Trace 找到过敏信息第一次丢失的位置。先确认原始输入和意图、实体抽取是否识别到过敏史；再检查短期记忆和 Prompt 组装是否携带；随后检查检索证据、工具调用参数与返回值；最后检查最终模型输入输出以及安全规则是否拦截。找到第一次丢失点后，再决定修复抽取、记忆、Prompt、检索、工具还是安全兜底，并把该案例加入回归集。

### 11.5 Trace 建议字段

```text
trace_id / span_id / parent_span_id
sequence
event_type
component_name
timestamp / latency_ms
status / error_type
input_summary
output_summary
intent / slots
retrieval_query
retrieved_document_ids / scores / sources
tool_name / argument_summary / result_summary
model_name / prompt_version
fallback_reason
safety_rule_hits
```

隐私合规要求：

- 不默认记录完整原始病历；
- 身份信息、联系方式、证件号等必须脱敏；
- 输入输出按最小必要原则保存；
- 敏感字段加密并实施权限控制；
- 记录访问审计与保留期限；
- 评测样本使用匿名化或合成数据。

## 12. 单元测试、性能测试和效果评测不能混为一谈

### 12.1 单元测试回答什么

单元测试通过能够说明：

- 函数和模块行为符合预期；
- 路由、数据模型、回退分支等没有明显回归；
- 部分异常路径可复现。

它不能说明 RAG 召回质量一定提升。

### 12.2 性能测试回答什么

吞吐量、P95、错误率能够说明：

- 系统在特定硬件、数据量和并发条件下的性能；
- 是否存在阻塞、超时或容量问题。

它不能说明答案正确。

### 12.3 RAG 效果评测回答什么

固定评测集上的 Recall@K、MRR、NDCG、答案忠实度、引用正确性与无答案识别指标，才能支持检索和回答质量结论。

面试时可以说：

> 当前自动化测试证明代码链路可复现、功能稳定；性能测试证明指定环境下的容量；检索质量仍需用人工标注的独立评测集做消融实验。三类证据不能相互替代。

## 13. 一分钟项目回答模板

> AGI-saber 是一个 Python/FastAPI 后端、Vue 前端的个人办公 Agent，核心能力包括知识库问答、记忆、工具调用和长任务执行。我重点学习和参与的是 RAG 与 Agent 质量评测链路。RAG 入库时采用父子分块，用小块提高细粒度检索能力，再补全父段落保证上下文；检索侧组合语义检索、BM25 和可选图检索，用 RRF 做异构排名融合，再用 Rerank 优化候选顺序。评测侧会用人工标注的 gold chunk 构建离线集，通过 Recall@K、MRR 和 NDCG 分别评估召回与排序，用可回答和不可回答样本校准无答案阈值。线上问题则依靠 Trace 沿输入、状态、检索、工具、生成和安全拦截逐层定位，并把 Badcase 加入回归集。当前代码已经具备父子分块、混合检索、重排失败回退和评测基础设施，但阈值最优性、图路增益和生产级熔断仍需要进一步实验，不能过度宣称。

## 14. 面试术语纠错表

| 容易说错 | 正确说法 |
|---|---|
| 无答案预值 | 无答案阈值 |
| 便利阈值 | 遍历阈值 |
| RRF 是 Rerank | RRF 是排名融合，Rerank 是精排 |
| RRF 的 k 是另一种算法 | `k` 只是 RRF 的平滑常数 |
| Precision 是拒答率 | Precision 是系统判为正类的样本中真正为正类的比例 |
| F1 就是倒数相加 | F1 是 Precision 和 Recall 的调和平均 |
| BM25 可以精确找到正确答案 | BM25 擅长字面匹配，但不保证结果一定正确 |
| 单元测试全过证明 RAG 有效 | 单元测试证明代码行为；RAG 效果必须用标注评测集验证 |
| 图谱在“关系复杂时参与” | 应说明明确触发条件、实体关系查询和消融实验 |
| 当前已有完整熔断器 | 当前确认的是单次重排失败回退；三态熔断需按真实代码陈述 |

## 16. 复习建议

每个知识点都按以下结构练习：

```text
业务问题
→ 原方案的缺陷
→ 当前技术方案
→ 为什么不选其他方案
→ 如何用指标验证
→ 当前实现边界与下一步改进
```

每天至少完成：

1. 不看文档复述一次一分钟项目介绍；
2. 手算两道 Precision / Recall / F1；
3. 手算一个两路 RRF 示例；
4. 用一条 Badcase 画出 Trace 信息流；
5. 选择一个简历数字，说明它对应的测试条件和证据；
6. 明确说出一个项目尚未完成或尚未验证的地方。

面试目标不是把项目说得无所不能，而是做到：

- 技术链路讲得清；
- 方案选择讲得出权衡；
- 指标不会混淆；
- 代码实现和设计方案分得开；
- Badcase 能按证据定位；
- 不知道时不编造，能够给出验证方法。
