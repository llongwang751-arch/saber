# 01：从一句话进入系统，到一个任务完成

## 1. 先把五个名词分开

LLM 是生成和理解语言的模型；RAG 给它找当前可用的资料；工具替它执行真实动作；Workflow 规定步骤与依赖；Agent 在一定边界内选择下一步或工具。一个系统可以同时包含确定性流程和模型决策，没必要争论它“只能算哪一种”。

本项目就是混合形态：普通工具路径由模型输出 JSON 计划；报告路径使用预设四节点工作流；节点里面仍会使用模型写作和检索。官方也将预定路径的 Workflow 与动态选择流程/工具的 Agent 区分开。[LangGraph：Workflows and agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents)

## 3. 一次普通问题的主链路

下面是教学流程，不是逐行复制代码：

```text
Vue 聊天框
  → HTTP 鉴权、请求 ID、请求约束
  → AgentRegistry.get(user_id)
  → _dispatch
      → _prepare：记录本轮输入、提交记忆抽取、决定路由、装配上下文
      → _dispatch_mode：rag / rag_agent / react
      → _finalize：记录回复、记忆整理、快照与事件
  → 普通 JSON 响应，或经 SSE 向页面推送事件
```

关键数据不是只有 `content`：响应还可能带模式、意图/槽位、工具调用、步骤、RAG 轨迹、任务和 trace_id。看到这些字段也要继续核对来源：字段存在不代表本次都有内容。

### 追问：多轮对话是怎么做到的？

同一个用户会复用 Agent；最近消息写入短期记忆和聊天历史，再参与后续上下文构造。长期记忆补充跨请求信息。

但当前 `ChatRequest` 只有 `message`、`use_rag`，没有后端会话 ID。前端存在“最近会话”界面不等于后端每个会话各有 STM、任务和取消令牌。同一用户开多个聊天窗口要特别验证互相影响，详见第 04 章。

## 4. 三种模式：这是你必须背后的条件表

| 条件 | 模式 | 实际行为 |
|---|---|---|
| 开启 RAG，且知识库已加载，问题不触发组合任务关键词 | `rag` | 检索并生成回答 |
| 开启 RAG，且已加载，问题包含研究/调研/总结/报告/文档/方案/分析等词 | `rag_agent` | 强制使用研究、写作、审查、保存 DAG |
| 其余情况 | `react` | 尝试规划已注册工具；无可用计划时走直接回答等处理 |

这不是独立训练的三分类模型。不能因为响应里叫 `intent`，就说系统训练了意图识别器。业务层还有规则解析、工具 matcher 等，应该分层解释。

### 为什么之前让它用 write_document，它却说没有工具？

因为在输入框写一个工具名称，不会自动把工具注册到后端。当前默认普通工具主要是 `search_web`；沙箱和业务/Skill 工具按条件注册。文档保存主要是报告 DAG 的 `DocAgent` 调用领域方法，不意味着通用工具列表一定包含 `write_document`。

排查顺序应是：文档是否真的入库→RAG 开关与 loaded 状态→本次 route→工具/子代理注册表→节点结果→文档列表。只有聊天文字“我保存了”而无写入记录，不构成成功证据。

## 5. 报告任务完整拆开

```text
n1 research_agent：围绕任务收集知识库证据
        ↓
n2 writer_agent：基于研究结果形成 Markdown
        ↓
n3 review_agent：提出质量、风险、证据缺口意见
        ↓
n4 doc_agent：读取 n2 成文 + n3 审查信息，保存文档并回填 RAG
```

准确的依赖是：n2 依赖 n1；n3 依赖 n2；n4 同时依赖 n2 和 n3。最后一条不是单纯接收“审查后的新稿”。

ResearchAgent 对计划查询去重并限制数量，再逐次收集结果；Writer 负责成文；Review 生成意见；Doc 保存 Writer 内容，并携带审查信息。这是角色分工，不是四个不同参数规模的模型，也不意味着四台独立服务器。

### 两个当前限制，必须讲清楚

第一，审查不是硬门禁。没有“判定不通过→退回重写→再审查”的自动循环，也没有根据评审意见阻止保存的完备逻辑。若面试官问如何改：让审查输出结构化 `approved/issues`，运行时据此分支，限制修订次数，最终由用户确认或明确失败。

第二，强制 `rag_agent` 默认包含保存节点。宽关键词路由不等于明确写入授权；“总结文档，不要保存”不能当安全的只读提示词。改进需要将任务意图和写入授权分离成服务端结构化状态，在执行节点前校验，不能只补一句 Prompt。此处是改进建议，本次没有修改执行代码。

## 6. 动态计划是怎样产生的？

`llm_plan_graph` 把当前问题、工具描述和参数信息提供给模型，要求输出 JSON 计划，然后解析节点、工具名和依赖。工具必须在允许集合里；不支持任意“模型创造的工具”。一般 react 路径不任意开放子代理注册表。

可以用编译器类比理解：自然语言任务是输入，JSON 计划是中间表示，TaskGraph 是经过结构检查的执行图，GraphRuntime 是执行器。但它不是一个严格类型的完整编译系统：当前参数会经过字符串化，复杂嵌套结构和语义约束需要更强的 schema 校验。

当前还有一个值得代码审查的分支：图校验失败后，Agent 会清空依赖再尝试构图。这可能让本应串行的动作被并行执行。因此不能宣传“非法计划全部拒绝执行”。更稳妥的方案是返回结构错误、限定次数重新规划，必要时拒绝执行，绝不静默抹掉关键依赖。

### 追问：ReAct 到底在哪里？

项目保留 `react` 命名以及 Thought/Action/Observation 风格的执行摘要，但主要执行结构是“规划任务图→运行节点→必要时有限重规划”。不要直接把它讲成每一步都由同一个模型无限循环决定下一步的标准实现。看实际控制流，不看命名下结论。

### 追问：重规划与重试有什么区别？

重试是同一工具同一任务重新执行，适合短暂网络失败；重规划会改变后续任务图，例如换一个工具补充信息。`llm_replan` 受开关与预算限制，每次新增节点数也受限。实际 YAML 开启了相关开关；类的默认值不一定相同，演示时以加载后的配置为准。

## 7. 一条更适合业务面试的链路：猪场报告

源码入口：[farm_agent.py](../../internal/application/farm_agent.py)、[farm.py](../../internal/application/farm.py)。

业务价值不在“让模型计算所有指标”，而是用确定性程序计算关键数值，让模型负责理解请求和表达解释。

```text
CSV/XLSX 数据 → 校验与持久化 → 业务指标计算
用户问题 → 请求解析/缺参澄清/风险检查 → farm_copilot
        → 查询指标或生成报告 → 可选保存文档 → 后续知识检索
```

例如日期范围不明确时应澄清；关键字段缺失时应标记不可计算，不能让模型补数值。重复导入的幂等机制和工具执行重试幂等是不同层面的事，不能相互替代。

面试官问“为什么这不只是聊天 Demo”：展示导入数据、指标来源、异常解释、报告产物和用例回归，说明业务闭环。面试官再问“上线过吗”：如未真实上线，明确是已实现业务链路和工程控制、仍需真实环境验收，不能虚构用户量或收益。

## 8. Prompt Engineering 在哪里体现？

不是只写一句“你是专家”。至少要区分：路由/规划提示、研究提示、成文提示、审查提示、RAG 证据边界、记忆抽取提示、上下文约束。

一个可维护的提示需要定义输入、任务、可用资料、输出格式、失败和拒答条件。业务事实放在检索和工具输出中，运行权限放在服务端校验中，不能让 Prompt 同时承担这两项职责。

改提示的验证方式：固定数据集版本与模型配置，比较相同 case 的输出、轨迹、成本和失败分布；不要只比较一条“看起来更顺”的回答。当前策略控制面不等于已完成所有 Prompt 的自动注册和优化。

## 9. 本章练习

1. 找出 `use_rag=False` 时为什么不会进入固定报告 DAG。
2. 在编辑器里跟踪 n4 从哪里拿到 Writer 内容，确认 Review 没有覆盖成稿。
3. 对照工具注册和模型请求体，解释“Tool Use 已有”与“原生 Function Calling 未接入”的区别。
4. 为“只总结，不保存”写一份应有行为说明：授权字段、路由、节点检查、审计和回归用例。只写方案，不在演示环境随意测试写入。
5. 用两分钟解释整条请求链，不说“各种模块协同工作”这类无法核对的话。
