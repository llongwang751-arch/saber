# 05：从测试集，到可信评测、A/B 和策略迭代

## 1. Benchmark 和测试集不是一个东西

测试集是一组输入和预期；Benchmark 是还固定了运行协议、被测配置、打分方法和比较方式的一套基准。Excel 可以方便人工标注，JSONL 更方便版本管理和机器执行。格式本身不决定可信度。

项目的主要机器执行资产是 JSONL：每行一个完整 JSON 对象，可以包含多轮消息、工具参数、证据 ID、风险和轨迹要求。不是把一列问题导入页面就完成评测建设。

## 3. 先建立四层真实性分级

| 层级 | 实际运行 | 能证明 | 不能证明 |
|---|---|---|---|
| Replay 回放 | 读取预制 baseline/fixed 输出并评分 | 评分器、回归比较、门禁和界面 | 模型真实答对 |
| 组件测试 | 真实核心类 + 确定性替身/临时存储 | 状态、错误、隔离、算法契约 | 外部服务稳定、真实模型质量 |
| Local/HTTP 实跑 | 调用当前 Agent 或服务 | 当前配置下的实际链路行为 | 自动等于生产效果；后端可能仍是替身 |
| 在线实验 | 真实合格流量、随机分配、实际曝光和反馈 | 满足前提下的线上因果比较 | 任意离线提升都会在线生效 |

当前截图中的 baseline 0/12、fixed 12/12 是 Replay 示例。必须主动说清楚，否则面试官只要问“模型请求日志在哪里”就会暴露口径问题。

## 4. 一条正确的用例长什么样？

下面是符合项目 EvalCase 契约的教学示例，并非本次已入库或已执行的测试。问题的真实证据必须提前准备，不能仅凭示例中的数字认定业务事实。

```json
{
  "case_id": "study_rag_budget_001",
  "scenario": "rag",
  "turns": [{"role": "user", "content": "星槎计划一期预算是多少？"}],
  "expected": {
    "required_content": ["320万元"],
    "evidence_ids": ["budget-001"],
    "retrieval_k": 3,
    "min_recall_at_k": 1.0,
    "answerable": true
  },
  "risk_tags": [],
  "metadata": {"input": {"use_rag": true}}
}
```

`metadata.input.use_rag` 是测试输入开关；`expected` 是评分答案，不能发送给被测模型，也不能用它判断该不该走 RAG。否则就是标签泄漏。现有 `_case_use_rag` 已明确从输入 metadata 取值。

一个高质量用例还应明确：数据版本、用户/租户、前置记忆、允许的工具和副作用、故障注入、最后状态、标注来源、所属子集。预期应描述允许行为集合，不要要求模型复读唯一措辞。

## 5. Adapter 为什么重要？

源码：[adapters.py](../../internal/evaluation/adapters.py)、[schemas.py](../../internal/evaluation/schemas.py)。

ReplayAdapter 读取预制输出。LocalAGISaberAdapter 逐条执行 user 消息，再把最后响应和事件归一到 AgentOutput。它不会把数据集里预填的 assistant 消息全部原样注入；也不自动为所有 case 创建独立干净的 Agent。

当前 Local 会观察前后记忆快照得到 memory_writes，但未完整填充 memory_reads；flush 的超时返回也需要更严格处理。因此不能说“所有记忆读写指标已自动真实采集”。需要源头埋点或组件专用测试。

HTTPAdapter 会发送 turns 等评测输入，但项目原生 `/api/chat` 的 ChatRequest 不消费完整 turns。只调用一次这个接口不能自动复现一段多轮脚本；真实 HTTP 多轮评测应逐轮发请求并管理会话，或接一个明确支持对话注入的评测入口。

归一化 Trace 可能补齐最终响应事件，这是适配行为，不是原始 LLM 调用证据。要证明真实执行，需要同时保存 adapter 类型、运行环境、后端身份、工具结果来源和实际请求/耗时。

## 6. 项目评测器在评什么？

源码：[evaluators.py](../../internal/evaluation/evaluators.py)。当前组合 16 项指标，包括意图、必需槽位、工具选择、工具参数、工具结果、内容、证据、Recall/MRR/nDCG、可回答性、记忆、兜底、隐私、边界和轨迹。

只有适用指标进入总体分数；case 的通过还要求适用指标通过，不是平均分高就一定过。S0/S1 安全项另有硬门禁，不能被其他高分抵消。

`required_content` 主要是确定性包含检查，不是完整语义正确性或忠实性判断。证据 ID 正确也不代表答案的每个断言受证据支持。当前不能宣传已经完整集成 RAGAS、全量 LLM-as-Judge 或专业领域事实审核。

## 7. RAG 三个公式与一个例子

```text
Recall@K = 前 K 个结果中相关证据数 / 全部相关证据数
RR@K = 1 / 首个相关证据排名；前 K 无相关证据则为 0
MRR = 各问题 RR 的平均
DCG@K = Σ ((2^相关等级 - 1) / log2(排名 + 1))
nDCG@K = DCG@K / 理想排序的 DCG@K
```

例：金标是 A、C，返回 B、C、D。Recall@3 为 1/2，RR@3 为 1/2。即使 C 支持部分答案，另一个必要事实 A 仍没找齐。nDCG 用于区分“非常相关”和“略相关”的排名；没有可靠分级标注就别假装等级很精确。

另加回答层：正确性（回答是否正确）、忠实性（断言是否受给定证据支持）、引用准确性、引用覆盖率、有/无答案判断。它们与检索指标相关，但不可替代。

### 如何用 LLM Judge？

这是建议扩展：先写明确 rubric 和正反例，再用人工双人标注集校准 Judge；盲化候选身份，检查顺序偏差、长度偏好和评审提示注入；保留“不确定需人工看”的出口。不能让出题、作答、评分同一个模型互相迎合，也不能把 Judge 分数当客观真值。

## 8. Agent 与记忆/Harness 用例怎么设计？

| 能力 | 正常用例 | 失败/边界用例 | 检查证据 |
|---|---|---|---|
| 澄清 | 参数齐全后执行 | 缺城市/日期先问，不猜 | 实际槽位与工具参数 |
| 规划 | 先查后写 | 非法依赖、工具不存在 | DAG 和节点状态 |
| 工具 | 成功返回结构化数据 | 超时、429、畸形数据、重复响应 | attempt 与错误分类 |
| 多轮 | 后续引用前文 | 用户更正旧参数、话题切换 | 最后实际动作，不只回复文字 |
| 长期记忆 | 有用事实可召回 | 注入不得写入、跨用户不得读 | 写入来源、召回 ID、状态 |
| 持久化 | 重启后恢复 | 提交失败、投影失败、迟到删除 | 数据库/outbox/索引状态 |
| 取消与预算 | 预算内完成 | 取消后不启动新节点 | 时间和事件顺序 |
| 报告 | 根据证据生成与保存 | 不授权保存、审查不通过 | 文档实际变更与执行门禁 |

不同用例必须隔离状态。否则前一题写入“答案”，后一题召回，得分会虚高。持久记忆题需要明确 setup/turns/assert/teardown；真实服务评测使用专用账号和测试数据，不读写个人正式资料。

## 9. Benchmark 运行和证据保存

在 `final/`、项目依赖已安装的 Python 环境中执行：

```powershell
python -m pytest tests/test_rag_quality_eval_dataset.py tests/test_memory_harness_eval_dataset.py -q
python scripts/run_benchmark_suite.py --output-dir runtime/interview-benchmark --database runtime/interview-benchmark.db
```

第二条会创建本地评测库和报告；再次运行会新增记录。脚本本身定位为离线确定性 Benchmark，不用于证明调用了真实模型。不要误用业务数据库路径。

应该保存：代码提交/工作区状态、数据集 checksum、adapter、策略 manifest、模型与提示版本、语料/索引版本、实际后端、随机种子（适用时）、原始输出、归一 Trace、指标、耗时和错误。预制的 latency 不能当真实模型 P95。

## 10. 数据集怎么长大，才不是为代码量身做题？

从真实脱敏问题、业务规则、历史失败、边界和人工设计的对抗例组合采样。拆开发集、阈值校准集和最终测试集；相关文档、近重复问法、同一实体或同一时间段要防止跨集合泄漏。不要只随机打散高度重复问题。

报告分层结果：任务类别、数据来源、长度、可回答性、多跳、风险和租户隔离。整体提升但高风险子集退化，不应直接发布。小样本下报告样本量和区间，不把个位数差异说成显著提升。

旧测试集用于回归，新留出集用于检查泛化；发现 Badcase 后将其加入开发回归集，避免一直用同一个测试集调参。合成数据应标注合成来源，医疗事实需合格人员与版本化资料审核。

## 11. Badcase 与离线策略闭环

```text
不可变数据集版本 → 基线/候选执行 → 指标和 Trace
              → 失败分类与根因 → 有限改动
              → 同 case 回归 + 安全门禁
              → 人工审批 → 显式激活/回滚
```

Badcase 关闭要有同一不可变 case 在候选 run 真实通过的证据，不能管理员手写“已修复”就当质量改善。离线策略绑定 manifest 和成对 run，使比较可审计；离线审批通过也不等于线上已分配流量。

源码：[service.py](../../internal/evaluation/service.py)、[strategy.py](../../internal/evaluation/strategy.py)、[store.py](../../internal/evaluation/store.py)。

源码：[experimentation/service.py](../../internal/experimentation/service.py)、[assignment.py](../../internal/experimentation/assignment.py)、[runtime.py](../../internal/experimentation/runtime.py)、[statistics.py](../../internal/experimentation/statistics.py)。

有实验控制面、稳定分组、合格受众身份、曝光账本、请求终态、反馈归因、样本/停止规则、SRM 和分析等实现。默认关闭，当前只接入满足条件的只读 `rag` 请求，不把会写文档的 `rag_agent` 任意放进试验。

运行时白名单主要是 RAG `top_k`、`no_answer_threshold`；控制组不覆盖参数，候选组按请求局部覆盖，不修改全局配置。并不是随意在线切换模型、整个 Prompt 或工具权限。

生产模式要求真实鉴权、合格受众与共享非 SQLite 存储等前置条件；还校验运行环境组件清单/可信指纹，避免“manifest 写的是 A，实际跑的是 B”。这些代码和测试不是已获得真实线上效果的证明，本次没有开展真实流量实验。

### 面试必答四问

- 分配和曝光不同：分到候选组但没执行候选逻辑，不应算候选曝光。
- SRM 是实际分组比例异常，提示分流/采样问题，不等于效果显著性检验。
- 稳定按用户分组可减少同一用户来回切换；分析单位还需匹配分配单位，不能把同一用户多次请求当完全独立样本。
- 频繁看显著性然后随时停会引入偏差；要预先确定样本与停止规则，或使用事先选定的序贯方案。

对于 top_k：更多候选可能提高召回，也会增加长度、延迟和噪声。主指标可选真实任务成功/有效反馈，护栏至少看错误、延迟、拒答和安全，不是只看点击率。

## 13. “自进化”真实含义是什么？

[evolution.py](../../internal/evaluation/evolution.py) 从失败证据推导受限 RAG 参数建议，记录证据快照与校验值，经不同审核者确认后物化为离线策略候选。

准确称呼是“证据驱动、人工审批的受控策略迭代”。它不会自动训练模型、重写任意代码、扩大权限或无人审核发布。面试时主动限定范围，比只说“系统会自己学习”更有工程可信度。

## 14. 本章练习

拿一个失败 case，填写：输入→预期→实际→错误阶段→原始证据→最小修复→防回归测试。随后写出哪些分数来自回放、哪些来自核心类执行、哪些仍缺真实模型验证。

最后自问：如果页面显示 100%，你能用数据库、adapter 和请求记录解释这 100% 的分母及来源吗？不能，就先别把它放进简历指标。
