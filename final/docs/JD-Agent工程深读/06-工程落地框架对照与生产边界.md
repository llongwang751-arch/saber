# 06：工程落地、框架对照与生产边界

## 1. 怎么解释“没有用 LangChain，但符合 Agent 岗位”？

先承认实际依赖：项目使用 Python/FastAPI 与自建编排模块；当前 requirements 没有 LangChain/RAGFlow。然后展示你理解框架所解决的共同问题：模型适配、工具 schema、状态图、持久化、流式事件、上下文和评测。不要声称自己用过未实际接入的框架。

| 概念 | 本项目对应位置 | 面试重点 |
|---|---|---|
| 模型适配 | `internal/llm/llm.py` | 请求格式、超时、真实/替身边界 |
| 工具抽象 | `internal/tools/tools.py` | schema、权限、错误和副作用 |
| 图编排 | planner + TaskGraph + GraphRuntime | 状态、依赖、条件和重规划 |
| 上下文/记忆 | `promptctx/` + `memory/` | 取什么、不取什么、如何一致 |
| 持久状态 | `repo/` + 应用存储 | 快照和可安全恢复的差别 |
| 评测闭环 | `evaluation/` | 不可变版本、证据和比较 |

LangChain 提供 Agent 组装能力，官方当前的 `create_agent` 建立在 LangGraph 运行时之上；LangGraph 则提供更底层的状态图与长时任务编排设施。自建实现可用于理解原理，但不能未经验证便说与其持久执行等成熟能力等价。[LangChain Agents](https://docs.langchain.com/oss/python/langchain/agents)、[LangGraph Overview](https://docs.langchain.com/oss/python/langgraph/overview)

RAGFlow 的官方定位覆盖文档数据处理、混合检索和可视化 Agent 编排。对本项目而言，可以比较文档解析质量、索引管理、集成成本与评测接口，不能把它简单说成“另一个向量库”，也不能声称当前项目已接入。[RAGFlow 官方介绍](https://ragflow.io/)

### 如果面试官问：为什么不直接用现成框架？

可答：项目目标包括理解和对齐既有 Go 行为，自建核心便于直接控制路由、任务图、记忆提交和评测契约。代价是需要自己承担持久调度、安全和兼容性成本。面向真实交付时，我会按需求评估复用成熟框架，而不是为了展示自研坚持重做所有基础设施。

## 2. Python 工程问题会问什么？

### FastAPI 的 async 路由为什么还会卡？

`async def` 不会自动把阻塞的 requests、同步数据库或 CPU 计算变成非阻塞。本项目模型调用是 requests，聊天入口把执行放到线程/线程池，SSE 使用队列传事件。需要一起限制请求并发、节点并发和后台作业，避免线程与连接数膨胀。

GIL 不意味着线程毫无价值：网络 I/O 等待可以重叠；CPU 密集任务另考虑进程或专用服务。提高 worker 数还会复制进程内 Agent 状态，不能只做吞吐压测而忽略会话一致性。

### Pydantic 用在哪里？

HTTP/评测/实验的数据契约、字段范围和不允许的额外字段。类型校验不等于业务授权；用户提交一个格式正确的 user_id，也不能获得那个用户的数据。实验 runtime 参数还用白名单限制允许改变的字段。

### 事务和锁怎么分工？

线程锁保护单进程数据结构；数据库事务和条件更新保护跨进程持久状态。RLock 不能阻止另一台机器抢同一任务，outbox 租约也不自动替代外部 API 幂等。

### 配置为什么容易出问题？

类默认值、YAML、环境变量和请求覆盖可能不同。面试要展示加载后的安全配置摘要，但不要输出凭证。当前代码使用 StrEnum，Python 3.10 不应继续作为兼容承诺；建议以项目验证过的 Python 3.11 环境学习和演示。

## 3. 业务、存储、前端怎样串起来？

[main.py](../../main.py) 构建依赖和服务；[application/api.py](../../internal/application/api.py) 安装身份、业务和评测等入口，并为用户构建 Agent。

本地 ApplicationStore 支持应用持久化，SQLAlchemy/Alembic 管理其表结构；外部 Postgres、Milvus、ES、Neo4j、Kafka 等由基础设施层接入。不要简单说“所有数据都在一个库”，也不要认为启动时连接不上一个可选组件，所有功能就必然不可用。

前端是 Vue + Pinia，主要入口为 [App.vue](../../web/src/App.vue)，聊天状态和 SSE 分别在 [chat.js](../../web/src/stores/chat.js)、[useSSE.js](../../web/src/composables/useSSE.js)。工具轨迹、评测、文档和实验页面消费不同接口。

旧 `frontend/index.html` 与 `web/` 构建资源的关系应从实际服务静态挂载确认；修改一个未被当前页面使用的文件，会出现“代码改了但界面没变”。

Skill 广场管理 Prompt Skill 的安装/启停与用户工具注册。GitHub 发现是只读元数据能力，不等于已安全安装执行任意第三方代码；Skill 也不是模型微调。

## 4. 安全边界要用具体例子讲

| 边界 | 当前可见机制 | 仍需验证/完善 |
|---|---|---|
| 身份 | JWT、密码哈希、用户作用域 | 开发密钥替换、轮换、权限策略 |
| 数据 | 用户过滤、文档与图路径归属 | 全路径越权回归、跨会话问题 |
| 输入 | 请求长度检查、schema | 无 Content-Length 的流式上限、文件内容解析安全 |
| 工具 | 注册白名单、结构化错误、沙箱校验 | 真实用户审批、副作用幂等 |
| 提示注入 | 证据分隔与过滤 | 多语言/编码/间接注入，工具端强约束 |
| 日志 | request_id、Trace | 凭证/隐私脱敏、访问控制、留存与清理 |
| 策略变更 | 白名单覆盖、审批、证据校验 | 真实业务审批职责与应急回滚演练 |

当前 AuthService 对缺失/不安全 secret 存在开发密钥回退，不能把“服务启动了”当生产密钥合规证明。检查 status 与部署策略，不能使用配置样例中的数据库密码或开发 secret 上线。

生产中还要防 SSRF、恶意文件、租户数据外发和工具返回注入。它们是上线审查清单，不是本次已全部实现或完成渗透测试的结论。

## 5. 监控什么，而不只是“接了监控”？

需要区分当前已有事件/状态/指标接口与真正建成的生产仪表盘和告警。代码中有 Trace、评测统计和运行状态，不代表已采集完整实时 token 账单或长期业务 SLA。

建议指标按层收集：

| 层 | 指标 | 排故意义 |
|---|---|---|
| 请求 | 请求量、错误率、首事件/总耗时 P50/P95/P99 | 用户是否感到卡顿 |
| 模型 | 调用次数、超时、输入/输出 token、成本 | 费用与外部模型瓶颈 |
| 检索 | 各路命中/错误/延迟、空检索、拒答、精排失败 | 找不到还是生成错 |
| Runtime | 排队、并发、attempt、取消、失败节点 | 是否重试风暴或卡住 |
| 记忆/投影 | 队列长度、flush 超时、outbox 年龄/重试/死信 | 信息新鲜度与一致性 |
| 实验 | 分流比例、有效曝光、终态缺失、反馈成熟度 | 分数是否受数据缺失污染 |

P95 需要足够样本并标明统计窗口；只对成功请求算延迟会掩盖超时。RAG 相关性下降属于效果问题，HTTP 错误率可能仍为零。

## 6. “怎么又卡住了”的诊断模板

1. 记录操作、时间、账号、request_id/trace_id，避免只截最后的空白。
2. 浏览器网络面板检查请求是否发出、HTTP 状态和 SSE 是否持续收到事件。
3. 若服务无响应，检查线程/连接占用、请求超时、模型和工具等待。
4. 若 RAG 空，检查 route、loaded、各路模式与错误、权威文档和投影状态。
5. 若轨迹 `{}`，对比原始返回、存储内容和前端选取的字段，并确认是不是回放样例。
6. 若回答说保存成功，检查实际 document ID、内容和列表刷新，不只信文本。

`/healthz` 和 `/readyz` 当前都直接返回 ok，只能作为兼容性基础探针；依赖状态需另外核验。中间件 `wait_for(call_next)` 也不能直接证明长 SSE 的整个响应生命周期都被同一超时覆盖。

## 7. 最小演示环境与生产环境分开

最小学习环境：验证过的 Python、依赖、独立本地应用数据库、开发账号、短文档；真实模型演示再配置模型和 Embedding。若外部检索不可用，就展示 local 模式并标明，别在本地降级时宣传已验证三路。

生产准备应包括：凭证与 TLS、数据库备份/迁移演练、共享状态、多会话隔离、权限审批、工具幂等、外部依赖容量、任务恢复、监控告警、真实质量集和回滚。是否需要 Kubernetes 应由规模决定，不是生产化的同义词。

当前迁移头为 `0017_memory_supersession_provenance`，升级前应备份自己的业务库。本次文档任务不自动执行业务库迁移或部署。

## 8. Go/Python 复刻怎么讲才不露怯？

[run_go_python_conformance.py](../../scripts/run_go_python_conformance.py) 冻结 Go `845e8f7`，导出该提交树到临时目录，记录证据并运行 Go 测试，再运行 Python 行为契约。当前 Go 工作区的未提交修改只用于溯源观察，不应污染冻结基线。

可讲：对固定 Go 基线开展路由、报告 DAG、检索、记忆、工具和 HTTP 等契约对齐，另有 Python 业务与评测扩展。

不能讲：文件数一样所以完全复刻；一个测试通过所以任意输入都等价；Go 基线有某个不安全行为所以 Python 必须永久保留。兼容性目标与修复目标发生冲突时，要显式版本化、加迁移说明和新测试。

## 9. 面试官要求再接一个业务，你怎么设计？

以设备维护工单为教学例，不表示项目已有该功能：

1. 明确用户角色、数据源、允许自动做的动作及必须确认的动作。
2. 只读查询与写工单分离；schema 明确设备 ID、故障、时间、证据与幂等键。
3. 确定性代码校验设备权限和必填字段；模型负责解析和澄清。
4. RAG 检索维修手册，引用版本与条款，不能把模型猜测当操作规程。
5. 用户确认后创建工单，保存外部 ID 和结果，超时可查证而非盲重试。
6. 评测正常、缺参、越权、恶意手册、工具超时和重复提交；灰度前明确护栏。

这个回答同时覆盖 JD 的工作流稳定、规划、Tool Use、RAG 和落地，不需要堆架构缩写。

## 10. 当前最优先的工程改进顺序

这是基于本次源码阅读的建议，不是本次执行开发计划：

1. 写入动作授权、非法图拒绝、工具副作用幂等，先解决可能误执行的问题。
2. conversation/request/task 状态拆分，配合持久作业与取消边界。
3. 真实调用 Trace、记忆读取埋点、多轮评测协议和独立测试集。
4. 精确上下文预算、图谱多来源建模、各检索后端故障链路验证。
5. 在上述基础上做真实多实例联调、容量验证和受限在线实验。

能演示并讲清这些取舍，是项目的价值；未经验证的“全面生产化”反而是容易被追问击穿的表述。
