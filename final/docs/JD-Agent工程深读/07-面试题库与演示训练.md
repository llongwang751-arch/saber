# 07：80 个面试问题、讲述模板与演示训练

使用方式：先遮住回答自己说，再回对应章节查源码。这里是回答骨架，不是必须逐字背诵的台词；“我负责”的内容必须替换成你真实参与过的模块。没有任何题库能保证涵盖面试官所有问题。

## 一、项目定位与请求链路（01～10）

### Q01：用一分钟介绍项目。

这是一个 Python/FastAPI 的 Agent 应用平台。用户可基于上传文档问答或生成报告，系统提供检索、任务图、工具执行、用户记忆和轨迹；外围用版本化测试集、Badcase、门禁及受控策略审批做迭代。当前有可演示业务链路，但真实模型质量和生产可靠性要用各自证据证明。

追问准备：选择一条真实业务讲完，不要把功能目录全部念一遍。参见 00、01 章。

### Q02：它解决什么业务问题？

把业务资料查询、数据指标解释和报告产出串起来，同时留下证据与执行记录。以猪场报告为例，指标由确定性代码计算，模型负责理解和解释。若没有真实使用数据，不能编节省多少人力的指标。

### Q03：一次请求经过哪些组件？

前端→HTTP 鉴权和请求约束→按用户获取 Agent→准备消息和上下文→路由→检索/任务图/工具→最终回复与持久化→JSON 或 SSE。源码从 handler 的聊天接口跟到 agent 的 `_dispatch`。

### Q04：Agent 和 Workflow 有什么区别？

Workflow 预定路径，Agent 在受限环境里动态选择动作。项目报告使用固定工作流，普通工具计划有模型决策，是混合架构；不是每个节点用了 LLM 就变成完全自治系统。

### Q05：项目意图识别怎么实现？

由 RAG 开关和 loaded 状态、组合任务关键词、工具 matcher 与业务解析共同决定。没有看到独立训练的通用意图分类模型，不能把响应里的 intent 字段当作模型训练证据。

### Q06：三种路由是什么？

RAG 可用时，普通问题进入 rag，命中报告/研究等宽关键词进入 rag_agent；其余走 react。要结合实际配置和日志，不能只根据问题里出现某个工具名推断执行路径。

### Q07：为什么让它调用 write_document 会失败？

用户提到工具名不等于后端已注册。当前文档写入主要通过固定报告 DAG 的 DocAgent；先查本次路由、知识库状态和工具注册，再查写入结果，不能归结为“模型不听话”。

### Q08：四个子代理分别做什么？

Research 收集证据，Writer 成文，Review 提意见，Doc 保存 Writer 内容及相关信息并入库。n4 同时依赖 n2/n3；没有自动重写和审查硬门禁，不能说审查后必然变成合格稿。

### Q09：为什么需要多 Agent？

角色提示、输入输出和轨迹更清晰，便于分别评测与替换。代价是更多模型调用、延迟和错误传播；简单问答直接 RAG 更合适，不能为“多 Agent”把每件事拆四次调用。

### Q10：这个项目是 Demo 吗？

不宜二选一。它已有业务持久化、任务执行和质量控制代码，超出只返回固定文本的页面演示；但部分评测是回放，生产状态、权限和真实效果仍有缺口。准确介绍已验证范围，比一句“不是 Demo”有说服力。

## 二、规划、Runtime、Harness 和工具（11～25）

### Q11：计划如何生成和验证？

模型按工具描述输出 JSON，解析成 TaskGraph，并检查工具集合和依赖结构；报告路径用固定节点。当前非法图有清依赖兜底风险，应说明并建议拒绝/限定重规划，而不是声称所有非法计划都被阻断。

### Q12：DAG 为什么不能有环？

例如 A 等 B、B 又等 A，就没有可执行起点。计划应在执行前检查环与缺失依赖；确需循环改稿时应作为有预算的控制逻辑，而不是无界循环依赖。

### Q13：Runtime 是什么？

执行任务图的状态机与调度器：找 ready 节点、执行工具/子代理、更新结果和失败状态、处理预算与事件。核心是 graph_runtime.py，不是 LLM 自己在操作系统里随意执行。

### Q14：Harness 是什么？

约束和验证 Agent 执行的工程设施集合，包括上下文、权限、工具契约、预算、观测、持久化、评测等。本项目这些能力分布在多个模块，不能把 Harness 等同一个 Prompt 或测试页面。

### Q15：节点是完全异步并行的吗？

当前按 ready 批次启动线程并等待整批结束，信号量控制并发；存在批次屏障。更细粒度调度可在单个节点完成后立即激活下游，但需要处理共享状态与取消竞争。

### Q16：重试与重规划区别？

重试同一动作处理暂时故障；重规划根据观察改变后续动作。两者都需要预算，重规划还要再做工具与依赖校验，不能靠反复调用模型“总会成功”。

### Q17：配置 max_retries=3 是几次调用？

当前普通工具循环最多三次总尝试；不是首次加三次。重模型 Skill 有单次尝试等特殊处理，回答必须看实现，不猜配置名含义。

### Q18：哪些错误该重试？

短暂网络/服务不可用可以在预算内重试；参数和权限错误应直接反馈。当前 4xx 分类也包含 429 的不重试，需要完善限流语义。写操作还必须考虑是否已经成功。

### Q19：如何防工具重复写入？

用业务幂等键、执行账本、结果查询和外部唯一 ID，区分未知结果与明确失败。项目未实现所有工具的全局 exactly-once，曝光请求幂等不等于写报告幂等。

### Q20：停止按钮是否真能停？

前端停止接收和服务端取消是两步；令牌只能协作取消，阻塞外部调用和已提交副作用未必停止。同一用户还共享部分取消范围，需请求级隔离。

### Q21：Racing 适合什么？

多个可替代只读来源争取首个成功结果，降低尾延迟，但增加调用成本。输家取消是协作式的；不能对两个有副作用的动作竞速后认为只发生一次写入。

### Q22：有快照就能断点续跑吗？

不能。快照记录状态，持久执行还要处理节点认领、版本、崩溃窗口和外部副作用。当前有恢复基础，但不能承诺进程重启自动安全续跑所有动作。

### Q23：Function Calling 和项目 JSON 规划有什么区别？

项目让模型在普通文本内容里生成 JSON，然后本地解析执行；当前 llm.py 没发送原生 tools 声明，也没处理对应的原生工具消息闭环。两者都能实现 Tool Use，但协议和可靠性约束不同。

### Q24：项目支持 MCP 吗？

有名为 new_mcp_tool 的 HTTP JSON 适配层；完整 MCP 初始化、发现和协议调用不能仅凭函数名宣称已实现。可以展示结构化错误适配，协议兼容范围应单列测试。

### Q25：沙箱能保证安全吗？

Docker 的权限、网络与资源约束降低风险，但安全取决于实际后端、挂载与配置。Prompt 禁令和模型生成 confirm=true 不是可信人工审批；本地后端不能当成容器隔离。

## 三、RAG、知识图谱与答案质量（26～42）

### Q26：为什么选 RAG，不直接微调？

本项目要查询可更新的私有文档并引用来源，检索能独立更新资料并做权限过滤。微调更适合改变行为/表达等目标，不能直接替代文档版本、访问控制和引用；项目当前不是模型训练平台。

### Q27：父子分块有什么价值？

子块提高定位粒度，父块补上下文；代价是重复与长度增加。当前是字符切分，默认子 200/重叠 50，对应父 800/重叠 100，不是 token 切分。

### Q28：Embedding 服务挂了怎么办？

分块仍可保存在本地并走词法能力，但不应报告为真实语义检索。检查 mode、投影和错误，后续补向量/重建；不能只凭 uploaded/loaded 就认为全部索引成功。

### Q29：三路召回分别解决什么？

向量处理语义近似，关键词处理精确术语，图谱补充实体关系。用多跳和精确术语子集做消融，不能因为第三路存在就声称整体效果必然更好。

### Q30：三路每次都跑吗？

不。受后端可用性和开关影响，当前 hybrid 两条主路成功后才尝试 KG；单查询主路还不是全部并行。必须看本次 Trace 的实际来源。

### Q31：RRF 是什么，为什么不用原始分数相加？

RRF 按 `Σ weight/(k+rank)` 融合不同来源排名，避免直接混合不同标度的分数。当前 k 默认 60，语义/关键词各权重 1，图权重单设，semantic_weight 不是当前实际融合系数。

### Q32：RRF 分数 0.03 意味着什么？

只是当前路数、排名和 k 下的融合分数，不是 3% 正确概率。不能和 0.3 的精排阈值直接比较，改变查询数也可能改变分布。

### Q33：改写为什么可能使效果更差？

可能丢失否定、时间、实体或改成另一个问题。当前还有追加原问题再截断导致原问题未进入检索列表的边界；应保留原查询名额，并评测改写保真和召回贡献。

### Q34：Reranker 用的是什么？

当前有 LLM 精排与 local_overlap 备用，Cross-Encoder 是可选配置，不能假装默认已跑。查看 backend/标记和输入预览，区分精排成功与降级。

### Q35：怎样避免没有答案还硬答？

空证据拒答，成功精排时用对应分数阈值控制；校准有/无答案两类错误。证据阈值只解决一部分风险，最终生成还需引用和忠实性检查。

### Q36：为什么 top_k 不是越大越好？

增加召回也增加噪声、重复、token 和延迟，还可能挤掉关键上下文。要一起看召回、答案质量、拒答和成本，不能只比较检索命中数。

### Q37：知识图谱怎么构建？

模型抽实体关系 JSON，类型白名单校验，Neo4j 按用户和实体名合并；问题实体作种子有限跳扩展，映射回分块并参与 RRF。不是训练 GNN，也不是完整社区摘要 GraphRAG。

### Q38：图谱当前最大数据建模问题？

实体上记录的 chunk/doc 来源可能被后续同名实体覆盖，难以保留多文档出处。建议单独建 Chunk-MENTIONS-Entity 和关系证据版本，解决消歧与来源追溯。

### Q39：怎么证明图路有效？

固定数据和其他参数，比较关闭/开启图路在多跳、实体关联子集上的检索与回答指标，并记录延迟。直接事实题满分不证明图推理价值，人工关系错误也要计入成本。

### Q40：文档里的恶意指令如何处理？

文档是证据而非授权；做来源边界、内容过滤、租户隔离和工具权限。当前过滤不保证防住所有注入，尤其写入和执行命令要靠服务端约束，不能只加一句系统提示。

### Q41：检索命中正确但回答错，怎么定位？

核对最终交给模型的父块、版本、截断和引用，再看回答断言是否受证据支持。候选正确不代表最终上下文正确，也不代表模型忠实生成，不能继续盲调召回。

### Q42：本地检索能撑大规模吗？

当前本地是词法扫描保留 TopK，不能假称已建倒排/ANN。先测候选扫描、CPU、内存和 P95；规模上去再考虑索引和外部检索服务，提供实测而非估算宣传。

## 四、记忆、多轮和上下文（43～55）

### Q43：长期记忆和 RAG 有什么不同？

长期记忆保存用户相关事实/偏好，强调更正、时效和隐私；文档 RAG 保存业务资料，强调版本、证据和权限。可以共享检索思想，但不能混成一个无来源文本池。

### Q44：什么信息应该进入记忆？

用户明确的稳定偏好、有后续价值的事实等；保留来源、时间和范围。助手猜测、检索文档命令、凭证和临时噪声不应直接升级为长期用户事实。

### Q45：记忆是实时写入的吗？

有异步抽取队列，所以回复与持久化可能有时间差。flush 只是在限定时间等待队列屏障；未提交作业在进程崩溃时可能丢失，关键更正需要更强的确认语义。

### Q46：用户更正记忆怎么做？

新旧条目建立 supersedes/superseded_by 溯源，旧项变 superseded，召回过滤 active。数据库版本 CAS 避免覆盖并发更新；不能只追加一条矛盾事实让模型自己选择。

### Q47：PG、缓存、Milvus、Neo4j 怎么保持一致？

权威记忆与 outbox 同事务提交，成功后更新缓存，worker 异步投影并重试/对账。这是最终一致性设计，外部投影竞争、迟到删除和多实例仍需验证。

### Q48：outbox 能保证所有记忆不丢吗？

只能覆盖已提交事务产生的投影事件，无法保障尚在进程内等待抽取的输入。必须区分抽取作业持久性和投影持久性，两者不是一条队列。

### Q49：记忆怎样召回和遗忘？

按用户/active/类别等筛选后结合相似度与重要性排序；后台做去重、合并、衰减和低重要性过期淘汰。阈值以实际配置为准，还要验证调用频率是否影响衰减。

### Q50：全局记忆是所有用户共用吗？

不是。这里主要是用户级跨请求长期记忆。共享企业知识需要独立命名空间、ACL 和来源治理，不能直接公开用户私有记忆。

### Q51：项目已支持独立多会话吗？

后端当前按用户缓存一个 Agent，ChatRequest 没有 conversation_id。前端会话列表不能证明 STM/任务/取消已按会话隔离；这是应如实说明的缺口。

### Q52：上下文都有哪些来源？

画像、规划、任务记忆、工具状态、约束、相关回忆，按模式 schema 选择和装配。还有历史/RAG 等进入最终请求的其他内容，不能把槽位总预算当整个请求预算。

### Q53：token 超限怎么处理？

当前按字符裁剪条目，优先丢低优先级来源，不是精确 tokenizer。改进应统一计算最终请求并留输出空间，对历史和工具结果做有保真的压缩，不能简单删掉权限条件。

### Q54：rag_agent 会用到所有上下文槽位吗？

当前 schema 没单独注册 rag_agent，未知模式回退 chat。应查看实际装配结果，不能根据“报告复杂”推断自动使用 react 全槽位。

### Q55：怎么评测记忆，而不是测数据库 CRUD？

除了持久化，还要测抽取是否应写、召回相关性、实际使用、更正、遗忘、隔离和污染。当前 Local adapter 的 memory_reads 采集未完整接通，需要补埋点或使用专用组件断言。

## 五、评测、A/B、监控和演进（56～70）

### Q56：Benchmark 与测试集区别？

测试集是题和标注，Benchmark 还固定协议、配置、指标与对比规则。只有 Excel 问题列表不是完整 Benchmark，换模型和语料后也不能不说明就横比成绩。

### Q57：测试集用 Excel 还是 JSON？

项目机器资产是 JSONL，便于嵌套多轮/工具/轨迹和版本管理。人工可先表格标注再校验转换；不要把一个包含预置 outputs 的 JSONL 当真实输出日志。

### Q58：现在有多少题？

本次核对前五个 EvalCase 资产共 69 条，另有 9 条独立 RAG fixture。它们包含回放和组件标注，数量不等于真实模型调用数；未来应重新统计并报告来源。

### Q59：为什么 12/12 不代表模型满分？

演示 fixed 输出是预制 Replay，得分证明评分规则与回归闭环可运作。真实质量需要固定模型/语料/输入，保存实际调用和结果后重新评测。

### Q60：Recall@K、MRR、nDCG 分别看什么？

Recall 看相关证据找全程度，MRR 看第一条相关结果的位置，nDCG 看分级相关的排序质量。三个都是检索侧，不能替代答案事实正确性和忠实性。

### Q61：如何防评测数据泄漏？

expected/oracle 不进入被测输入、不控制路由；按文档/近重复/实体等划分集合；case 间隔离状态。当前 `_case_use_rag` 取 metadata 输入开关而非证据金标，就是一处具体防泄漏措施。

### Q62：多轮评测如何做？

固定初始状态，按用户轮次执行，保留真实助手响应，检查最后实际动作和中间澄清。项目原生 chat 不消费 HTTP Adapter 发送的完整 turns，一次 POST 不能自动证明多轮复现。

### Q63：为什么安全指标不能只算平均分？

越权、隐私泄漏等严重失败可能被大量简单题稀释。项目用 S0/S1 硬门禁独立阻断，整体分数和是否允许发布是不同结论。

### Q64：LLM-as-Judge 有哪些风险？

偏好长答案、候选顺序偏差、评审提示注入和同源模型偏差。需要人工校准、明确 rubric 和不确定出口；项目当前确定性包含检查不等于已完成全面语义 Judge。

### Q65：Badcase 怎么闭环？

按同一不可变 case 保存预期、实际和失败证据，定位根因，候选 run 实际通过后再关闭，并检查其他 case 回归。不能仅修改 issue 状态就声称修复有效。

### Q66：离线比较和 A/B 区别？

离线是固定题集配对比较，在线是合格流量分组后的真实曝光与结果。离线审批不产生线上流量，统计前提、延迟反馈和分析单位也不同。

### Q67：项目在线实验能改什么？

当前范围限定只读 RAG 的 top_k/no_answer_threshold 等白名单参数，按请求覆盖且默认关闭。不是任意在线改模型、权限或整个工作流，也没有本次真实流量收益证明。

### Q68：什么是曝光、SRM 和统计单位？

曝光表示实际执行实验逻辑，不只是被分组；SRM 检查分组比例是否异常；统计单位应匹配随机化单位，不能忽视同一用户多个请求的相关性。它们各自解决不同的数据可信问题。

### Q69：项目“自进化”是什么？

根据评测证据生成受限 RAG 参数建议，经其他审核者批准后形成候选策略。准确称为受控策略迭代，不是模型自行训练、修改代码或无人审批发布。

### Q70：线上要监控什么？

请求错误/延迟、模型调用与成本、各检索路状态、工具重试与取消、记忆/outbox 积压、实验曝光和反馈完整性。已有 Trace 不等于生产监控大盘和告警已全部建立。

## 六、工程、交付与个人贡献（71～80）

### Q71：为什么用 Python/FastAPI？

利于 LLM 应用、schema 与测试迭代，已有生态适配成本较低；但同步 I/O、并发状态和资源管理仍要自己处理。以实际工程取舍回答，不说“Python 天生适合一切 AI”。

### Q72：异步接口为什么仍需线程池？

模型请求和部分数据库调用是同步阻塞的，要避免占用事件循环。线程池适合 I/O，但总并发要限额；CPU 密集计算和跨进程状态是另一个问题。

### Q73：怎么从单机扩到多实例？

先拆分 user/conversation/task/request 状态，使用共享持久存储、任务认领和幂等，再做负载均衡、连接池与容量验证。当前进程内 AgentRegistry 不会随 worker 增加自动共享状态。

### Q74：readyz 为 ok 为什么还不能回答？

当前 readyz 直接返回 ok，不实际检查模型/数据库/检索依赖。要另看 status、配置和一次真实链路；也要区分响应头返回与整个 SSE 结束。

### Q75：Python 是否完全复刻 Go？

对冻结 Go 845e8f7 进行了若干关键行为契约对齐，脚本可导出冻结树和运行测试。没有任意输入全行为等价的证明；要附上本次测试范围与 Python 扩展，避免绝对承诺。

### Q76：岗位要求 LangChain/RAGFlow，你用过吗？

如未实际使用就直说本项目是自建，解释工具、状态图、上下文与检索的对应概念，并提出一个最小迁移实验验证适配。不要把看过官方文档包装成生产使用经验。

### Q77：如何验证一个功能真的执行了？

看真实 adapter/后端、请求 ID、输入输出、工具 attempt、耗时与持久产物，必要时查外部服务。UI 标签、空事件、助手宣称和预制回放都不能单独作为执行证明。

### Q78：如果让你接一个新的业务工作流？

先澄清目标与权限，再定义读写分离工具 schema、缺参澄清、幂等与审批，接入证据和 Trace，建立正常/失败/越权/重复提交评测，最后灰度。可用第 06 章设备工单例子展开。

### Q79：你个人最有价值的贡献是什么？

用真实事实填：我负责的模块→遇到的问题→定位证据→修改取舍→自己跑过的验证→仍未解决的边界。不能把整仓库、原 Go 作者或 AI 辅助完成的工作全部归为自己的独立成果。

### Q80：下一步最值得做什么？

先解决写入授权、非法图和副作用幂等；再完善会话/请求状态、真实 Trace 与多轮评测；然后做上下文预算、图来源和真实多实例验证。说明优先级依据是风险与可验证收益，不是继续增加名词。

## 七、三种讲述长度

### 30 秒开场

> 我准备的是一个 Python Agent 项目，核心是知识库问答和报告工作流。它把检索、任务图、工具执行、记忆与轨迹串起来，并用版本化评测和门禁验证改动。我会重点讲自己实际掌握的【模块】，也会区分回放演示和真实模型执行，避免混用效果指标。

### 3 分钟技术展开

前 30 秒讲业务；接着 60 秒画请求路由和报告 DAG；再用 45 秒解释三路召回与记忆；最后 45 秒讲一个你真实复现过的失败及验证。没有亲自复现前，不要把文档中的潜在风险讲成你已经修复并上线的事故。

### 10 分钟演示脚本

| 时间 | 演示 | 必须解释的证据 |
|---|---|---|
| 0～1 分 | 说明业务和本次运行模式 | 真实模型/本地降级/回放分别是什么 |
| 1～3 分 | 专用测试账号上传短文档，问一个独有事实 | 文档 ID、RAG mode、命中内容 |
| 3～5 分 | 明确要求生成并保存报告 | n1～n4 状态、实际文档产物、审查边界 |
| 5～6 分 | 问资料中没有的事实 | 无答案处理，不制造依据 |
