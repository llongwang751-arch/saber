# 04：记忆系统、上下文预算与多轮状态

## 1. 先回答“记忆”和“上下文”有什么不同

记忆是系统保留的信息；上下文是本次模型调用实际能看到的信息。数据库里保存了十万条记忆，不代表模型每次看见十万条；模型能看见本轮检索证据，也不代表这些证据自动成为用户长期记忆。

项目里至少要分清五类状态：

| 状态 | 内容 | 生命周期与用途 |
|---|---|---|
| 短期消息 STM | 最近用户与助手消息 | 多轮连续性，超出窗口移出 |
| 用户偏好 Preference | 语言、称呼等键值 | 后续回答风格与画像 |
| 长期记忆 LTM | 分类事实、经历、规则等 | 持久化、召回、更新和遗忘 |
| 任务记忆 Task Memory | 当前任务、步骤、结果摘要 | 工作流执行相关上下文 |
| 文档知识库 RAG | 用户上传/报告生成的材料 | 按证据检索，不等于个人画像 |

“全局记忆”要先问全局的范围。当前可讲用户级跨请求长期记忆；不能说所有用户的私有记忆共享。企业公共知识要有单独命名空间、读写 ACL、版本和维护责任。

## 3. 一句话如何变成记忆？

以“以后请用中文回答，我现在负责甲猪场”为例：

```text
用户输入 → 最近消息/聊天记录
         → 提交异步抽取任务
         → 来源和内容检查 → 提取候选事实 → 分类/置信处理
         → 权威记忆事务 + outbox
         → 提交成功后更新进程内缓存
         → 后台更新向量/图投影

后续问题 → 召回候选 → 用户/状态/类别等过滤 → 排序 → 上下文槽位
```

当前有用户输入来源和完整问答来源的抽取路径，分别给予不同置信处理；问答抽取以用户问题为锚，避免只把助手自己说的话当用户事实。偏好抽取强调用户来源，候选还有安全过滤。

这些都是启发式与模型判断，不意味着不会误记。当前请求进入时也存在偏好快速更新路径，完整抽取的过滤不能自动证明所有写偏好入口都同样受保护。要沿每条写入路径分别测试。

### 追问：为什么不能把助手回复全部存成长期记忆？

因为助手可能猜错。如果猜测先进入记忆，下一轮又被当可信事实召回，就形成自我强化污染。应保存事实来源、时间、置信度和适用范围；检索材料中的指令也不能升级成用户长期偏好。当前 source 标签和过滤是基础，不是完整事实验证系统。

## 4. 异步写入为什么快，代价是什么？

`AsyncMemoryWriter` 用单个后台线程串行消费 FIFO 队列，避免每轮回复都等待抽取、Embedding 和写库。submit/stop 通过状态锁协调；flush 用队列屏障等待此前任务完成，便于测试读取稳定状态。

但是进程内队列不是持久消息队列。进程突然退出时，未提交抽取任务可能丢失；flush 超时也不能当作“已经写完”。若业务必须保证用户更正落库，要对关键更正同步提交，或把抽取作业先写到可恢复任务表。

重要区分：持久 outbox 保障已提交记忆的投影更新；它不能拯救尚未进入数据库事务的抽取任务。

## 5. 记忆更正：不是简单追加一条矛盾信息

用户先说“我负责甲场”，后来更正为“是乙场，之前说错了”。应该既让新事实生效，也保留它替代谁的来源链。

当前 Item 有状态、version、hash、superseded_at、supersedes/superseded_by 等信息。事务可以同时更新旧项的被替代状态和新项的来源链接；召回优先过滤到 active 记忆。迁移 `0017_memory_supersession_provenance` 补充相关溯源。

```text
旧记忆 A：active → superseded，指向 B
新记忆 B：active，supersedes 包含 A
召回：保留 B，过滤 A；审计时仍能知道更正历史
```

CAS（比较并交换）用预期版本检查更新是否基于最新状态，避免两个并发修改互相覆盖。它保护数据库变更，不代表跨所有外部索引已经线性一致。

## 6. 为什么权威库和向量库不能随便一起写？

如果先更新缓存、再写数据库失败，当前进程会“记得”一条从未持久化的事实。如果先写 PG，再写 Milvus 失败，重启后 PG 与检索索引不一致。

当前生产记忆路径采用的思路是：

```text
同一个数据库事务
  ① 提交记忆变更（版本检查）
  ② 写待投影 outbox 事件
事务成功
  ③ 更新缓存；冲突时重新加载权威状态
后台 worker
  ④ 认领 outbox → 投影 Milvus/Neo4j → 标记完成或重试
```

Postgres outbox 认领使用行锁/跳过已锁记录、租约和重试；失败累计后进入需要处理的状态，还有对账修复。这提供最终一致性的工程基础。

仍要保留边界：投影版本/hash 检查不自动解决所有跨实例竞争；删除后缺少足够持久的 tombstone/version 保护时，迟到写入可能让旧项复活；真实多实例、租约超时、网络分区需要专项联调。SQLite 本地投影账本测试也不能证明实际 Milvus/Neo4j 集群一致性。

## 7. 召回、合并与遗忘

主上下文 RecallSource 调用 LongTerm 的过滤召回：用户作用域、active 状态、类别、标签和时间等过滤后，结合相似度与重要性选候选。当前主要混合分数为 `0.7 × similarity + 0.3 × importance`；这是记忆召回公式，别和 RAG 的 RRF 混淆。

没有向量时存在词法降级。需要用缺失向量、空查询、相似旧事实等用例检验，而不是只测试“完全一样的句子能找回”。

长期记忆整理包括：重要性衰减、近重复去重、相近内容合并、过期且低重要性淘汰。`plan_consolidation` 先形成变更计划，`consolidate_committed` 提交后再改缓存，避免整理失败留下半更新内存。

参数要看实际配置。当前 YAML 的衰减率、合并阈值等与方法兜底默认值不同，不要只背函数中的常数。还应验证重复整理是否按预期时间增量衰减；按 created_at 反复乘衰减可能使遗忘速度与调用频率耦合。

### 追问：记忆图每次都会参与回答吗？

不是。项目有 GraphMemory/MemoryManager 图记忆能力，但主上下文装配注册的 RecallSource 走 LongTerm 召回。必须验证具体挂接与调用路径，不能因为有 graph_memory.py 就说主回答总是图扩展召回。

## 8. 上下文槽位比“把所有东西拼上去”好在哪里？

当前注册六类来源：用户画像 Profile、任务规划 Planner、任务记忆 TaskMem、工具状态 ToolState、约束 Constraints、相关回忆 Recall。

不同模式使用不同 schema；来源并发取数、单槽位裁剪、按优先级做总裁剪，再渲染成中文段落。可以清楚回答“这段信息从哪里来、为什么被丢弃”，也能对个别来源故障降级。

三个源码细节：

1. 名字叫 token_budget，但实现使用 `len(item.text)`，总默认 2400 也是字符预算；中文、英文和代码的 token 比不能固定按一个倍率换算。
2. 裁剪针对槽位文本，不覆盖 system 模板、历史消息、RAG 父块、工具参数及预留输出的完整模型请求。真正精确预算应在发请求前统一计数并预留输出空间。
3. schema 注册为 chat/tool/react/rag，没有单独 rag_agent；未知模式在 assembler 中回退 chat。不要假定报告模式自动装配了所有 react 槽位。

当前裁剪按完整条目取舍：第一条过长可能让该槽位一条也留不下；全局裁剪优先丢低优先级项，但 required 标记不等于绝对不可丢。生产上关键权限不能依赖“某条约束文字一定留在 Prompt 里”。

### 如何进一步优化上下文？

建议顺序：保留不可丢的任务与授权状态→精确 token 计数→对历史做有来源的摘要→工具结果分级截断→长期记忆去冲突→跟踪每类上下文对成功率的贡献。摘要需要保留更正、否定、单位和日期，不能只追求更短。

以上是演进方向；当前不能宣称已实现自动摘要压缩、全请求精确预算或自动最优上下文选择。

## 9. 用户隔离与会话隔离是两层

AgentRegistry 当前按 user_id 缓存一个实例；默认短期窗口是 5 轮、约 10 条消息，恢复也加载近期记录。它支持用户级状态隔离，但一个用户的多个会话共享实例，可能共享任务、偏好更新和取消范围。

建议的状态键设计：

| 范围 | 推荐键 | 示例 |
|---|---|---|
| 身份/长期偏好 | tenant_id + user_id | 回复语言 |
| 对话短期状态 | tenant_id + user_id + conversation_id | 当前指代、最近消息 |
| 工作流状态 | task_id | 节点与产物 |
| 单次执行控制 | request_id | 取消、deadline、attempt |

这是建议模型，不是当前 ChatRequest 已有字段。多实例还需要缓存失效、共享持久状态、实例回收策略，不能简单加 Uvicorn worker 数量就认为会话状态一致。

## 10. 记忆怎么评测？

至少测：应写入、不得写入、能召回、不能越权召回、更正后只使用新事实、重启恢复、过期遗忘、并发冲突、投影失败后恢复、删除后迟到事件不复活。

分开“记忆抽取质量”和“存储工程正确性”：固定抽取结果可以测事务与隔离，但不能证明真实模型准确判断哪些内容值得记。完整 Agent 还要测它是否真正使用了召回，不是数据库里有记录就算成功。

关联测试：[test_memory_harness_eval_dataset.py](../../tests/test_memory_harness_eval_dataset.py)、[test_memory_transactional_projection.py](../../tests/test_memory_transactional_projection.py)、[test_memory_consistency_parity.py](../../tests/test_memory_consistency_parity.py)。

练习：围绕“甲场→乙场”写一条时间线，标出每一步的缓存、数据库和向量索引状态；注入写库失败与投影失败，说明用户此时应该看见什么。不要用线上真实个人信息做实验。
