# P3 真实在线 RAG 实验控制面验收

日期：2026-09-14

## 结论

项目已经把在线实验接入真实 `/api/chat` 与 `/api/chat/stream` 请求，而不是在评测页随机生成一组数字。当前版本只允许改变请求级、只读的 RAG 参数 `top_k` 和 `no_answer_threshold`；共享配置、Prompt、模型、工具和写操作均不在实验白名单内。

这套代码能证明分桶、曝光、反馈、统计门禁、安全暂停和审计链路按契约运行。仓库没有附带生产实验结果，因此不能声称某项策略已经带来线上提升。本地 SQLite 或内部演练流量只能验证控制面，效果值与赢家必须保持不可宣称状态。

## 已落地能力

- 稳定分桶：使用服务端 HMAC 对租户、实验和用户做稳定分配；入组桶与实验分组桶相互独立。
- 分配不等于曝光：只有请求进入已加载的 RAG 路径、且曝光台账成功写入后才计数。
- 请求幂等：`X-Request-ID` 与租户、用户、消息及 RAG 开关的规范摘要绑定；同编号重试或换消息复用均返回 409，不会再次执行 Agent。
- 请求级配置：候选参数放入不可变执行上下文，不修改全局 RAG 配置，也不会串到并发请求。
- 盲态输出：普通聊天响应只返回不透明曝光编号，不返回分组、桶位、候选参数或策略 checksum；持久化 Trace 的公开读取也执行相同脱敏。
- 真实终态：曝光记录区分 completed、error、cancelled；只有 completed 才允许提交结果反馈。
- 结果归因：正负反馈通过不透明曝光编号关联，客户端不能提交 arm；按“每个真实曝光用户的首个有效反馈”聚合，未反馈用户仍进入意向治疗分母。
- 预注册：冻结主指标、聚合规则、基线率、最小可检测效应、显著性水平、功效、每组样本量、最短/最长周期、归因窗口、初始流量和分流比例。
- 固定停止与防偷看：达到预注册停止条件前隐藏分组结果、差值和显著性；人工不能因为中途走势有利而提前完成实验。
- 统计门禁：检查真实流量、完整终态、样本量、最短周期、归因成熟、分流比例异常（SRM）和可信 S0/S1 安全事件；不满足时效果、置信区间、p 值和赢家为空。
- 安全与完整性：可信服务端安全事件会自动暂停；预注册、HMAC 身份或候选编译产物漂移会失败关闭并留下审计记录。
- 可信运行身份：生产模式从只读组件清单、当前代码与配置、知识/索引摘要及部署制品身份计算 `RuntimeIdentity`；实验冻结完整证据摘要，并在启动、分流、曝光、反馈与分析入口重新校验。手填 64 位指纹不能通过生产就绪门禁。
- 人工生命周期：创建、提交、独立审批、灰度、加量、暂停、恢复、完成和回滚均带代次检查、幂等键与追加式审计；创建人不能自批，批准不会自动启动。
- 审计与故障兜底：每个实验的审计事件使用前序摘要和状态快照串成 SHA-256 链；严重安全信号即使在曝光终态写入失败时，也会先进入独立安全发件箱并触发紧急暂停。
- 分析稳健性：长期停留在 `started` 的曝光会阻断结论；归因窗口结束前保持盲态；相同监控快照按校验和去重，避免重复写入。
- 租户边界：服务端 JWT 身份决定租户和角色；离线提案数据库按租户共享，使同租户创建人和审批人能完成真实双人流程，同时保持跨租户隔离。
- 多实例真实性：生产结论同时要求应用数据库和租户评测数据库位于共享的非 SQLite 存储；本机租户 SQLite 不会被标记为生产证据就绪。

## 状态机

```text
draft -> pending_review -> approved -> canary -> running -> completed
                    \-> rejected       |          |
                                       +-> paused +-> rolled_back
                                       +-> safety_paused
```

`safety_paused` 只能由独立审批角色解除。任何状态变化都不会自动激活新的离线策略或生成“赢家”。

## 生产前置条件

要让页面显示“可下结论”，至少需要：

1. 开启强制认证并使用非开发 JWT 密钥；
2. 应用台账使用共享 PostgreSQL；
3. `AGI_EVAL_TENANT_DATABASE_URL_TEMPLATE` 指向所有副本共享、按 `{tenant_digest}` 隔离的非 SQLite 评测库；
4. 配置至少一名实验管理员和一名不同的审批人；
5. 使用服务端预置、明确可参与实验的业务账号，排除自助注册、管理员、测试和机器人账号；
6. 配置至少 32 字节的实验 HMAC 密钥，并在实验期间保持不变；
7. 由构建/发布流水线生成只读组件清单，配置 `AGI_EXPERIMENT_COMPONENT_MANIFEST_PATH`，并由部署控制器通过独立通道注入 `AGI_EXPERIMENT_COMPONENT_MANIFEST_SHA256` 及语料、索引、构建、Git 提交和镜像摘要；
8. 接入告警、备份、数据库高可用与组织自己的数据合规流程。

上述条件缺失时，系统允许内部演练，但不会把内部曝光包装成生产效果。

## 当前边界

- 本地 SQLite 能验证控制面和失败关闭语义，不能替代真实 PostgreSQL 多副本、连接池故障与高可用演练。
- 数据库内摘要链可以发现事件缺失、顺序变化和未同步改写；它不是外部 WORM 审计库。具备全库写权限的攻击者若能重算整条链，仍需靠数据库权限、外部日志归档和签名时间戳进一步约束。
- 当前分析会读取实验曝光与反馈再聚合；大规模流量应增加增量统计、分区与异步分析任务，不能把本地规模测试外推为生产吞吐。
- 生产镜像、只读挂载和真实基础设施仍需在实际 CI/CD 与部署环境中验收，仓库单测不能替代发布验收。

## 面试中的准确说法

可以说：

> 我把 RAG 参数实验接到了真实聊天请求，分配和曝光分开记账，候选配置只在请求上下文生效。实验预注册固定样本与周期，运行中隐藏分组结果避免反复偷看；只有真实合格流量、归因窗口、SRM、样本和安全门禁全部通过后才计算结论。创建、审批、启动和回滚由不同角色控制，SQLite 演练数据不会被说成生产提升。

不要说：

- “仓库已经证明线上提升了某个百分比”。
- “随机分桶就等于真实曝光”。
- “内部账号、测试账号和自助注册账号都能算生产用户”。
- “p 值小于 0.05 就会自动选赢家或自动发布”。
- “本地 SQLite 控制台可以支撑多副本生产实验”。
