# 腾讯面试官视角：AGI-saber 技术选型深挖

> 配套文档：`腾讯面试-AGI-saber七天速成学习手册.md` 负责代码地图和七天安排；本文负责回答面试官最爱追问的：**为什么用、能不能不用、为什么不用别的、有什么代价、怎么证明选择正确**。  
> 核验基线：2026-08-29 当前 `AGI-saber-python/final` 工作区。  
> 重要原则：下面同时写“当前实现”和“生产改进”。面试时必须明确区分，不能把设计方案说成已经上线。

## 0. 腾讯面试官真正想听什么

面试官通常不会满足于：

> 我用了 FastAPI、Milvus、Elasticsearch、Neo4j、RRF、Agent、RAG。

因为这只是技术名词清单。他会沿着以下路径追问：

```text
为什么有这个问题？
→ 为什么选这个技术？
→ 不用它能不能完成？
→ 最简单方案是什么？
→ 为什么不选其他同类方案？
→ 你付出了什么复杂度代价？
→ 什么时候这个方案会失败？
→ 你用什么指标证明它有效？
→ 当前代码真的实现了吗？
```

### 0.1 每道技术选型题的回答模板

用“问题—约束—候选—决策—代价—验证—边界”七步回答：

> **问题**：单纯向量检索对精确药名、编号和关键词不稳定。  
> **约束**：既要语义召回，也要精确匹配；两类分数尺度不同。  
> **候选**：只用向量、线性加权、RRF、学习排序。  
> **决策**：当前选向量 + BM25，再用 RRF 按排名融合。  
> **代价**：多一套 ES 基础设施，需要调权重，延迟和运维复杂度增加。  
> **验证**：做单路、双路、三路消融，比较 Recall@K、MRR、nDCG 和 P95。  
> **边界**：当前代码未完成正式消融，图路权重实现与注释还有不一致，因此只能说“已完成工程链路”，不能宣称“效果显著提升”。

### 0.2 “不用行不行”的正确回答

不要条件反射回答“不行”。大多数工程技术都可以不用，关键是规模和约束。

高分结构：

> 可以不用。小规模 MVP 可以用更简单的方案完成；当出现某个明确瓶颈后，再引入该技术。我们使用它不是为了堆栈，而是为了满足某项可验证约束。它带来的收益必须大于额外的开发、运维和故障成本。

## 1. 项目级架构为什么不是“一个大模型加一个聊天框”

### 面试官第一问

> 一个聊天助手为什么要 FastAPI、数据库、向量库、搜索引擎、图数据库、任务图和评测平台？是不是过度设计？

### 参考回答

> 如果目标只是单轮聊天，确实只需要前端、一个后端接口和模型 API。AGI-saber 的额外复杂度来自不同的非功能需求：RAG 需要文档版本、切分、索引和引用；长期任务需要工具编排、取消和恢复；多用户需要认证和租户隔离；线上质量需要 Trace、Badcase、回归和发布门禁。我的判断不是“组件越多越好”，而是按场景渐进启用：纯本地模式只用 FastAPI、Vue 和 SQLite 就能运行；Milvus、ES、Neo4j、Kafka 都是增强项，连接失败时允许降级。对于当前面试岗位，我会重点讲评测闭环，而不是把所有基础设施都说成强依赖。

### 什么时候算过度设计

- 用户和文档规模很小，却强制维护 Milvus、ES 和 Neo4j；
- 没有多跳关系问题，却引入知识图谱；
- 没有事件消费者，却只为“架构好看”引入 Kafka；
- 没有高并发和跨进程任务，却先上分布式任务平台；
- 没有标注集和消融实验，却宣称三路检索更好。

### 当前项目的合理定位

当前仓库更像“可扩展技术验证 + 面试演示系统”，不是已经在真实医疗流量下验证的生产系统。敢于说出这一点不会减分，反而说明你有工程判断。

## 2. 为什么用 Python + FastAPI

### 2.1 不用 FastAPI 行不行

可以。Flask、Django、Go Gin、Java Spring Boot 都能做后端。选择取决于团队、规模、性能和生态。

### 2.2 同类方案比较

| 方案 | 优势 | 劣势 | 更适合 |
|---|---|---|---|
| FastAPI | Pydantic 强契约、OpenAPI 自动生成、async 支持、AI/Python 生态好 | CPU 密集性能一般；async/sync 混用容易阻塞 | AI 应用、评测平台、快速 API 开发 |
| Flask | 极简、自由度高、学习成本低 | 契约、依赖注入、文档和大型项目规范要自己补 | 小服务、原型 |
| Django/DRF | ORM、后台、权限、生态完整 | 较重，异步和流式场景需要额外设计 | 管理后台、传统业务系统 |
| Go Gin/Fiber | 并发和资源效率好、部署单二进制 | AI SDK 和数据处理生态不如 Python 直接 | 高吞吐网关、稳定服务 |
| Spring Boot | 企业生态、治理、规范和团队协作成熟 | 开发和部署较重，AI 原型迭代慢 | 大型企业后端、复杂治理 |

### 2.3 为什么本项目选 FastAPI

1. 评测集、Agent 输出和 Trace 都需要强类型校验，Pydantic 可以直接作为边界契约；
2. 自动 Swagger 便于现场演示和接口自动化；
3. Python 适合数据清洗、指标统计、模型 SDK 和 pytest；
4. SSE、文件上传、JWT、后台执行都能在一个服务中快速实现；
5. 该项目的核心瓶颈主要是模型、Embedding 和数据库 I/O，不是 Python 本身的 CPU 算力。

### 2.4 面试官深入追问：FastAPI 性能一定好吗

不一定。FastAPI 的 async 只在正确使用非阻塞 I/O 时有优势。如果 `async def` 内直接调用同步模型 SDK、同步数据库或 CPU 密集计算，事件循环仍会阻塞。

正确方案：

- 原生异步 SDK：`await`；
- 同步 I/O SDK：线程池；
- CPU 密集：进程池；
- 长任务：任务队列；
- 下游保护：timeout、semaphore、限流、批处理和重试。

### 2.5 如何证明 FastAPI 选得合适

- API 开发速度和契约错误率；
- 并发下 RPS、P50/P95/P99；
- 慢 Embedding 期间 `/healthz` 是否仍可及时响应；
- schema 校验能否在边界拦截错误输入；
- 业务团队是否主要使用 Python。

### 当前代码证据

- `main.py`：组装配置、Infrastructure、UnifiedAgent 和 FastAPI；
- `internal/handler/handler.py`：主 API 和流式聊天；
- `internal/evaluation/api.py`：评测、策略审批与受控建议 API，数量以 OpenAPI 为准；
- `internal/evaluation/schemas.py`：Pydantic 严格契约。

## 3. 为什么用 Pydantic，不只用 dict

### 不用行不行

可以，但大量自由字典会把错误推迟到运行中。例如 `tool_calls` 字段拼错、严重度写成未知值、Trace sequence 为负数，都可能直到评测执行才发现。

### Pydantic 的优势

- 请求入口立即校验；
- Enum、范围、必填字段和嵌套对象可表达；
- `extra="forbid"` 防止静默接受拼错字段；
- 自动生成 OpenAPI；
- 测试、存储和 API 共用同一契约。

### 与 dataclass、TypedDict、JSON Schema 比较

| 方案 | 运行时校验 | 序列化 | OpenAPI | 适合场景 |
|---|---:|---:|---:|---|
| dict | 无 | 手写 | 无 | 快速临时代码 |
| TypedDict | 主要是静态检查 | 手写 | 无 | 内部类型提示 |
| dataclass | 默认无严格校验 | 需补充 | 无 | 纯 Python 领域对象 |
| JSON Schema | 强，但使用较底层 | 强 | 可接入 | 跨语言契约 |
| Pydantic | 强 | 内置 | 与 FastAPI 原生集成 | Python API 与数据契约 |

### 代价

- 模型演进需要兼容策略；
- 过度严格可能拒绝第三方 Agent 的宽松输出；
- Pydantic 版本升级有迁移成本。

当前项目通过 Adapter 先把不同 Agent 输出规范化，再交给严格模型，是比较合理的边界设计。

## 4. 为什么用 SQLAlchemy + Alembic

### 4.1 不用 ORM 行不行

可以直接写 SQL。对于少量、固定、性能敏感查询，原生 SQL甚至更清晰。

### 4.2 为什么当前选择 SQLAlchemy

- Dataset、Version、Run、CaseRun、Badcase、Annotation 有清晰关系；
- 本地 SQLite 和生产 PostgreSQL 可复用大部分模型；
- Session、事务和外键统一；
- 查询仍可写显式 `select`，不是只能依赖魔法 ORM。

### 4.3 为什么需要 Alembic

`create_all()` 只能让新数据库拥有当前表结构，不能可靠描述已有数据库如何从版本 A 升级到 B。Alembic 提供：

- 有序迁移链；
- upgrade/downgrade；
- 迁移历史；
- CI 中验证从空库升级；
- 数据与 schema 变更可审计。

### 与 Django ORM、原生 SQL 比较

- Django ORM：生态完整，但会把后端框架绑定到 Django；
- 原生 SQL：控制力强，但迁移、映射和跨数据库样板更多；
- SQLAlchemy：在 FastAPI 中更自然，兼顾 ORM 和显式 SQL。

### 代价与风险

- ORM 容易产生 N+1 查询；
- SQLite 与 PostgreSQL 语义并不完全一致；
- JSON 字段在 SQLite 和 PostgreSQL 的索引能力不同；
- 迁移必须在真实数据库验证，不能只测内存 SQLite。

### 当前项目怎么验证

`tests/test_evaluation_migrations.py` 检查完整迁移链、升级、降级、环境变量覆盖和旧 schema 接管；当前迁移头为 `0016_verified_runtime_identity`。

## 5. 为什么同时有 SQLite 和 PostgreSQL

### 不用 PostgreSQL 行不行

本地学习、面试演示和单用户小数据量可以不用，SQLite 足够。

### 不用 SQLite 行不行

生产统一使用 PostgreSQL 可以，但本地启动门槛变高，离线评测和 CI 依赖外部服务。

### 两者分工

| SQLite | PostgreSQL |
|---|---|
| 零运维、单文件、适合本地和测试 | 高并发、事务、索引、JSONB、运维能力成熟 |
| 适合评测演示、租户本地库、离线结果 | 适合共享业务数据和生产持久化 |
| 写并发有限 | 多用户并发更好 |

### 当前项目的设计

- 外部基础设施不可用时，本地用户、文档、RAG chunk、记忆和评测仍写 SQLite；
- 本地开发时，评测平台按租户拆分 SQLite，降低跨租户查询遗漏风险；
- 多副本生产环境通过 `AGI_EVAL_TENANT_DATABASE_URL_TEMPLATE` 使用所有副本共享的非 SQLite 租户数据库；SQLite 不能作为生产在线实验的证据存储。

### 面试官追问：数据库一租户一文件一定好吗

不一定。

优势：隔离简单、导出删除方便、查询不必每次加 tenant 条件。  
问题：租户很多时文件和连接管理困难，跨租户统计复杂，迁移和备份成本上升。  
生产替代：共享 PostgreSQL 加强制 `tenant_id`、行级安全策略，或按大客户独立库、小客户共享库。

## 6. 为什么用 SSE，而不是轮询或 WebSocket

### 6.1 三种方案比较

| 方案 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|
| 轮询 | 最简单、恢复容易 | 空请求多、实时性受间隔影响 | 低频进度查询 |
| SSE | HTTP 单向流、事件格式简单、浏览器支持重连 | 主要单向；代理缓冲和连接数要处理 | LLM token、Agent 进度 |
| WebSocket | 真正双向、低延迟 | 连接治理、鉴权、扩容、心跳更复杂 | 协同编辑、双向实时控制 |

### 为什么当前选 SSE

Agent token 和评测进度主要是服务端向客户端推送，双向能力不是核心需求。SSE 比 WebSocket 更简单，又比轮询实时。

### 不用 SSE 行不行

可以。评测 Run 当前同时提供 `/progress` 轮询，所以 SSE 只是体验增强，数据库中的 Run 状态才是事实来源。

### 当前实现与生产差距

当前评测 SSE：状态变化才推送、每 250 毫秒检查、客户端断开就结束生成器。尚缺：

- heartbeat；
- event id；
- `Last-Event-ID` 补发；
- 代理层关闭 buffering；
- 多实例下的共享事件源。

### 如何验证

- 断网重连是否重复创建任务；
- 任务完成但 SSE 丢失时，轮询能否恢复结果；
- 慢客户端是否造成内存堆积；
- 代理超时和浏览器并发连接限制；
- 取消后后台任务是否真的停止。

## 7. 为什么做父子分块，不直接固定长度切块

### 7.1 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| 固定字符/token 切块 | 简单、稳定 | 容易切断语义和标题关系 |
| 递归分隔符切块 | 尽量保留段落结构 | 仍可能跨语义边界 |
| 语义切块 | 边界更自然 | 需要模型/Embedding，成本和不稳定性更高 |
| 父子分块 | 小块召回精确、父块上下文完整 | 存储重复、关联和去重复杂 |

### 7.2 当前为什么选父子分块

长段落包含多个主题，整体向量可能稀释局部事实；只用小块又会缺少上下文。父子分块把“定位”和“阅读”分开：子块负责召回，父段落负责最终上下文。

### 不用行不行

小文档、FAQ、每条知识本身很短时，直接单块即可。只有当长文档出现“召回精确但回答缺上下文”时，父子分块才有明显价值。

### 当前代码事实

- 子块：200，重叠 50；
- 父块：800，重叠 100；
- 每个子块保存完整 `parent_content`；
- 返回时按完整父内容精确去重。

### 当前方案的代价

- 每个子块重复保存父段落，存储放大；
- 没有独立 `parent_id`，去重和更新不够优雅；
- 没有严格 Token budget；
- 精确字符串去重无法合并高度相似的相邻父块。

### 更好的生产设计

单独保存 Parent 表，Child 只存 `parent_id` 和 offset；召回后按 parent_id 聚合，以最高子块得分代表父段落；合并相邻区间，再按 token budget、来源多样性和分数装配。

### 如何证明有效

对比大块、小块、父子块：Recall@K、Context Precision、Faithfulness、平均上下文 token、入库耗时、索引体积和 P95。

## 8. 为什么需要 Embedding；不用行不行

### Embedding 解决什么

把文本映射到向量空间，使不同措辞但语义接近的内容能够匹配。例如“费用报销条件”和“哪些情况医保能报”可能没有相同关键词。

### 不用行不行

可以。政策编号、药名、产品代码等精确查询，BM25 可能更好；小型 FAQ 甚至可以规则匹配。

### 稀疏与稠密比较

- 稀疏检索：基于词项，解释性和精确匹配好；
- 稠密检索：语义泛化好，但可能召回“意思相近但事实不对”的内容；
- 混合检索：结合两者，复杂度更高。

### 模型选择要看什么

- 中文和领域语料表现；
- 向量维度、上下文长度；
- 归一化与相似度定义；
- QPS、批量接口、价格；
- 数据是否允许出域；
- 模型升级导致向量不兼容时的重建成本。

### 面试官追问：换 Embedding 模型需要做什么

不能只改模型名。要记录 `embedding_model/version/dimension`，建立新索引或双写，重算全量文档向量，用固定验证集比较质量与延迟，灰度切换后再下线旧索引。

## 9. 为什么用 Milvus，不用 FAISS、pgvector 或 ES kNN

### 方案比较

| 方案 | 优势 | 劣势 | 适合 |
|---|---|---|---|
| FAISS | 本地快、算法丰富、无服务依赖 | 持久化、多租户、过滤、分布式需自己做 | 单机实验、离线研究 |
| pgvector | 数据与元数据同库、事务和过滤方便 | 超大规模和独立向量运维能力不如专用库 | 中小规模、已有 PostgreSQL |
| Elasticsearch kNN | 关键词和向量统一 | 资源较重，向量能力和调优模型不同 | 已重度使用 ES 的团队 |
| Milvus | 专用向量库、索引和规模能力强 | 多一个组件，运维和一致性复杂 | 大规模向量检索 |

### 当前选 Milvus 的合理理由

项目已经把 BM25 放在 ES，关系数据放 Neo4j，Milvus 专注向量检索，职责清楚，也便于独立扩容和比较各路效果。

### 不用行不行

当前数据量和面试 Demo 完全可以只用 pgvector 或本地向量索引。选择 Milvus 更像为规模扩展预留，而不是当前唯一选择。

### 代价

- 文本元数据与向量分布在不同系统；
- 写入部分成功会产生一致性问题；
- Embedding 维度不匹配会导致查询失败；
- 备份、监控和索引重建复杂。

### 当前代码如何处理

- PG/SQLite 先保存 chunk 与 parent；
- Embedding 非空且维度匹配才写 Milvus；
- Milvus 不可用时跳过语义路；
- 当前本地降级不会使用已保存的 embedding 做向量搜索。

### 如何验证

规模曲线、Recall@K、P95、过滤性能、索引构建时间、重启恢复、部分写失败和模型换代重建。

## 10. 为什么还需要 Elasticsearch BM25

### 不只用向量的原因

向量擅长语义，但对精确药名、政策编号、版本号、缩写和罕见实体可能不稳定。BM25 利用词频、逆文档频率和文档长度归一化，精确词项匹配更可控。

### 不用 ES 行不行

可以：

- 小数据量用 SQLite FTS5；
- PostgreSQL 用全文检索；
- 已使用 OpenSearch 可替代；
- 只有语义问答且精确关键词不重要时可只用向量。

### 为什么当前用 ES

它提供成熟 BM25、分词、索引、过滤和生产搜索能力，适合与向量路做消融。

### 代价

- 中文分词器和词典需要领域调优；
- 多一套索引和一致性；
- 小数据量可能得不偿失；
- 当前代码本地降级不是 ES BM25 的等价替代，只是简化词法余弦。

### 面试官追问：BM25 为什么不是词频越高越好

BM25 对词频做饱和，避免某个词重复很多次无限提高分数；IDF 强调稀有词；还对文档长度做归一化，避免长文档因为词多天然占优。

## 11. 为什么用 Neo4j 图检索

### 图谱解决什么

向量和 BM25 返回“相似文本”，图谱回答“实体之间有什么关系”。多跳问题如“某政策适用于哪类人，这类人需要哪些材料”更适合显式关系遍历。

### 不用行不行

大多数普通知识库问答都可以不用。图数据库不是 RAG 标配。若没有稳定实体、关系 schema 和多跳测试集，引入图谱很可能只有成本没有收益。

### 与关系库递归查询比较

- PostgreSQL 递归 CTE 能做层级和简单图遍历；
- Neo4j 的图建模和多跳查询表达更自然；
- 若关系规模小、类型固定，关系库足够；
- 若关系不断扩展、多跳查询多，图数据库更合适。

### 当前实现事实

- 入库后在后台线程 best-effort 建图；
- 图服务可用时 Hybrid 路径会尝试图检索；
- 当前不是由“关系意图分类器”按需触发；
- Milvus 失败时当前逻辑会退成纯 ES，无法充分利用成功的 KG 路；
- 图权重代码与注释不完全一致。

### 面试高分说法

> 图谱在当前项目中是增强路线，不是主链强依赖。我会先按查询类型做离线切片，只有多实体、多跳关系问题显著受益时才保留；生产上再增加实体识别置信度和关系意图路由，避免每个问题都付图检索成本。

### 如何证明有用

准备关系型专属测试集，对比无图和有图的多跳 Recall、Answer Correctness、证据路径准确率、延迟和建图错误率。

## 12. 为什么用 RRF，不直接线性加权

### 候选方案

1. 原始分数直接相加；
2. Min-Max/Z-score 归一后加权；
3. RRF 按排名融合；
4. Learning-to-Rank 学习融合；
5. Cross-Encoder 统一重排。

### 为什么当前选 RRF

Milvus、BM25 和图路分数尺度不同，跨查询分布也不同。RRF 只使用排名：

```text
score(d) = Σ_i weight_i / (k + rank_i(d))
```

它无需训练数据，简单、稳健、易解释，适合项目早期。

### 不用行不行

- 只有一路检索：不需要融合；
- 分数能稳定校准：可以加权求和；
- 有大量点击或标注数据：Learning-to-Rank 可能更好；
- 候选少且可承担模型成本：可直接统一重排。

### RRF 的优势

- 异构分数无需统一量纲；
- 多路共同命中自然加分；
- 不被某一路极端原始分数支配；
- 参数少。

### RRF 的缺点

- 丢失原始分差：第一名略优和远优被相似对待；
- 固定权重不适应查询类型；
- 候选没召回就无能为力；
- `k` 和权重仍需验证；
- 不等于最终相关概率，不能直接拿来做无答案阈值。

### 当前代码的重要事实

- `k=60`；
- Milvus 语义路权重 `1.0`；
- Elasticsearch 关键词路权重 `1.0`；
- 图路使用 `kg_weight`；
- `semantic_weight=0.7` 只为配置结构兼容保留，当前不参与计分；
- 多查询结果还会再做一次无权重 RRF。

### 如何证明 RRF 优于替代方案

在固定候选上对比：线性加权、RRF、专用 reranker。指标看 nDCG、MRR、Recall@K、P95 和参数对验证集的敏感性。没有这组实验时，不能说 RRF 最优，只能说它是当前无训练数据条件下的稳健工程选择。

## 13. 为什么做 Query Rewrite，不直接搜原问题

### 解决的问题

- 多轮指代：“它需要什么材料？”
- 用户口语与文档语言不同；
- 一个问题包含多个表达角度；
- 原问题过短或省略实体。

### 与 Multi-Query、HyDE 比较

| 方案 | 思路 | 优点 | 风险 |
|---|---|---|---|
| 历史感知 Rewrite | 补全指代，生成自包含查询 | 多轮稳定 | 可能错误补实体 |
| Multi-Query | 生成多个同义查询 | 增加召回 | 成本、重复和漂移 |
| HyDE | 先生成假想答案再向量检索 | 对抽象问题可能有效 | 假想内容可能带偏检索 |

### 当前选择

当前使用历史感知 Multi-Query，最多三条；解析失败回退原查询。优点是可解释，风险比 HyDE 更容易控制。

### 不用行不行

单轮、实体明确的问题可以直接检索。Rewrite 应通过查询分类按需开启，否则每个请求都增加一次 LLM 延迟和费用。

### 如何验证

- 指代类和省略类问题的 Recall@K；
- 查询漂移率；
- 实体保持率；
- 额外 token、费用和 P95；
- Rewrite 失败时原查询回退是否生效。

## 14. 为什么需要 Rerank；LLM Rerank 与 Cross-Encoder 怎么选

### Rerank 解决什么

第一阶段检索追求召回，候选可能有噪声；第二阶段使用更强模型比较 query 与候选，提高前几名精度。

### 方案比较

| 方案 | 优点 | 缺点 |
|---|---|---|
| 无重排 | 快、便宜 | top 结果噪声可能大 |
| LLM listwise | 易接入、能理解复杂语义、可给解释规则 | 成本高、随机、JSON 失败、延迟大 |
| Cross-Encoder | 专用相关性、稳定、批量高效 | 需部署模型，领域适配可能要微调 |
| 商业 Rerank API | 接入快、效果通常稳 | 数据出域、费用、供应商依赖 |

### 当前为什么使用 LLM listwise

项目已有 LLM 客户端，无需另部署模型，能快速验证重排链路；失败回退 RRF，保证基本可用。

### 不用行不行

可以。若第一阶段 top-k 很准、延迟预算严格或没有 LLM Key，可以直接用 RRF。生产上如果重排调用量大，Cross-Encoder 通常更可控。

### 当前实现的限制

- 候选预览默认只取前 200 字；
- 分数 0～10 再除 10，不代表校准概率；
- 已有跨请求三态熔断，但真实服务故障注入与告警仍未验收；
- 没有专门验证重排对 nDCG 的增益；
- LLM 评分可能受候选顺序影响。

### 如何验证

固定候选集，对比无重排、LLM、Cross-Encoder：nDCG@K、MRR、P95、费用、超时率、顺序交换一致性。高风险证据不能只依赖随机 LLM 重排。

## 15. 为什么自定义 Agent Router，而不是所有请求都用 ReAct

### 所有请求都 ReAct 的问题

- 简单聊天也先规划，延迟和成本增加；
- 模型可能产生无意义工具调用；
- 随机性和失败点变多；
- 测试和安全边界更复杂。

### 当前三路主分发

- `rag_agent`：知识库可用且命中报告关键词，执行 Research→Writer→Review→Doc 固定 DAG；
- `rag`：知识库可用的普通问答；
- `react`：其余请求，内部可直接回答或调用单个/多个工具，不开放报告子 Agent。

`chat`、`tool` 仍存在于 Schema 与辅助判断中，但不是当前顶层稳定模式。报告判断沿用 Go `845e8f7` 的宽关键词规则，存在简单总结也触发文档保存的风险。

### 规则 Router 与 LLM Router 比较

| 方案 | 优点 | 缺点 |
|---|---|---|
| 规则 | 快、确定、好测 | 覆盖有限、维护规则 |
| LLM 分类 | 泛化好 | 成本、延迟、随机和越权风险 |
| 小分类模型 | 稳定、便宜 | 需要标注训练 |
| 混合 | 规则拦截高置信，低置信交模型 | 实现更复杂 |

### 当前选择的解释

当前先用规则选择模式，复杂任务再进入 LLM Planner。这样把大部分简单请求留在确定性路径，降低成本和工具误用。

### 如何验证 Router

单独建立路由评测集，统计每类 Precision、Recall、混淆矩阵、误调用工具率、平均延迟和 token。工具或医疗安全相关误路由应单独设高风险门禁。

## 16. 为什么用 TaskGraph，不只用普通 ReAct 循环

### 普通 ReAct 循环

模型一步一步决定下一个动作，灵活，但并行、依赖校验、恢复和确定性较弱。

### TaskGraph 的价值

- 显式依赖；
- 拓扑排序检测环；
- 独立节点并行；
- race group 可以选择第一个成功结果；
- 节点状态、错误、重试和快照可观察；
- 适合长任务恢复和测试。

### 不用行不行

两三步、强顺序、一次完成的简单工具任务，普通循环足够。只有当任务可并行、需要恢复或依赖复杂时，DAG 才值得。

### 与 LangGraph、Celery、Temporal 比较

| 方案 | 定位 | 优势 | 劣势 |
|---|---|---|---|
| 当前自定义 TaskGraph | 进程内 Agent DAG | 代码可控、易学习、依赖少 | 单进程、可靠性和生态弱 |
| LangGraph | LLM/Agent 状态图 | Agent 生态、状态和节点抽象成熟 | 框架学习和绑定 |
| Celery | 分布式任务队列 | 成熟异步任务、重试、worker | 工作流状态和长事务表达有限 |
| Temporal | Durable Execution | 强恢复、事件历史、长流程可靠 | 引入成本和运维复杂 |

### 为什么当前没用 LangGraph

为了对齐原项目逻辑、保留对 Planner、工具、快照和测试的直接控制，也便于展示底层原理。但如果目标是生产级长流程可靠执行，Temporal 或成熟工作流引擎比当前线程实现更合适；如果目标是快速构建 Agent 图，LangGraph 会减少样板代码。

### 当前局限

- 使用线程，不是跨进程 durable execution；
- 进程崩溃后的恢复能力有限；
- race loser 只标状态，未必真正停止底层 I/O；
- `time.sleep` 重试会占用线程；
- 没有分布式锁和任务所有权。

### 如何验证

依赖环、缺失依赖、并发上限、取消、节点超时、重试、进程中断恢复、重复执行幂等、race loser 副作用。

## 17. 为什么设计短期、长期、偏好和图记忆

### 一种记忆能不能解决

可以做简单版本，但不同信息生命周期不同：最近对话应快速淘汰，用户偏好要稳定覆盖，长期事实要检索，关系记忆要扩展关联。混在一个向量库里会导致冲突、污染和难治理。

### 四类记忆的职责

| 类型 | 生命周期 | 召回方式 | 风险 |
|---|---|---|---|
| ShortTerm | 最近几轮 | 顺序窗口 | 超长上下文 |
| LongTerm | 跨会话 | 语义 + 重要度 | 过期、冲突、错误事实 |
| Preference | 稳定键值 | 直接读取与工具补参 | 用户更改后覆盖问题 |
| GraphMemory | 关系扩展 | 一跳关系/中心性 | 错误关系传播 |

### 不用图记忆行不行

完全可以。没有关系型记忆需求时，长期向量召回足够。图记忆只有在“相关记忆不能只靠语义近邻发现”时才值得。

### 当前方案为什么有合并、衰减和淘汰

长期记忆无限增长会增加召回噪声、成本和隐私风险。当前配置通过相似度合并、去重、TTL、重要度和衰减控制生命周期。

### 记忆系统最危险的问题

- Prompt Injection 被写入长期记忆；
- 把第三方信息误认成用户身份；
- 旧偏好覆盖新偏好；
- 敏感凭证落库；
- 错误记忆通过图关系扩散。

当前 `memory_writer.py` 有凭证和注入检查，是值得向腾讯面试官展示的质量思路。

### 当前主链限制

`ContextAssembler` 已由主 `_prepare()` 通过 `_build_context_prefix()` 接入，多槽位装配失败时才回退旧记忆前缀。面试中应说明已接入的模式预算，也要承认真实长会话、注入内容和极限 token 条件仍需压力回归。

## 18. 为什么需要工具沙箱

### 不用行不行

如果 Agent 只调用只读、安全、远程 API，可以不用 Docker 沙箱。但只要允许执行命令、操作文件或运行生成代码，就必须建立隔离。

### 当前安全设计

- Docker/local/mock 三种 backend；
- 超时、输出大小、内存、CPU、进程数；
- 默认禁网；
- 只读根文件系统；
- 命令长度和 allowlist；
- Planner 工具范围限制。

### Docker 沙箱与进程沙箱比较

- 本地子进程：启动快，但隔离弱；
- Docker：文件系统、网络和资源隔离更强，但启动慢、守护进程依赖；
- gVisor/Firecracker：隔离更强，部署复杂；
- 远程沙箱服务：集中治理，增加网络与服务依赖。

### 仅靠黑名单为什么不够

命令可以编码、拼接、借助解释器绕过。高风险系统应使用默认拒绝、最小工具集、参数 schema、文件系统隔离、禁网、资源限制、审计和人工确认。

### 如何测试

路径穿越、命令拼接、超时、fork bomb、超大输出、网络访问、只读文件系统、取消后进程残留。

## 19. 为什么用 Kafka；不用行不行

### Kafka 解决什么

解耦主请求与事件消费者，例如审计、监控、异步索引和行为分析；事件可持久化、重放和扩展消费者。

### 当前项目是否必须

不必须。Kafka 不可用时事件回退日志，主链仍运行。当前没有展示大规模消费者，因此它属于增强能力。

### 与 Redis Stream、RabbitMQ、数据库 Outbox 比较

| 方案 | 优势 | 适合 |
|---|---|---|
| Kafka | 高吞吐、分区、长期日志、重放 | 大规模事件流 |
| RabbitMQ | 路由和任务队列成熟 | 可靠消息和工作队列 |
| Redis Stream | 轻量、已有 Redis 时方便 | 中小规模流 |
| DB Outbox | 与业务事务一致 | 避免双写丢事件 |

### 当前设计风险

业务数据写成功、Kafka 发送失败会不一致。日志回退只保证可见，不保证消息最终被消费。生产应采用事务 Outbox：业务事务内写 Outbox 表，后台发布 Kafka，成功后标记，支持幂等消费者。

## 20. 为什么 Agent 评测优先确定性规则，不全用 LLM Judge

### 候选方案

- 人工评测；
- 确定性规则；
- LLM-as-a-Judge；
- 混合评测。

### 对比

| 方案 | 优点 | 缺点 |
|---|---|---|
| 人工 | 专业、能判断复杂语义 | 慢、贵、一致性需要管理 |
| 规则 | 快、便宜、可复现、证据清晰 | 覆盖开放语义有限 |
| LLM Judge | 可扩展主观评判 | 偏差、随机、幻觉、成本 |
| 混合 | 兼顾确定性和语义 | 系统更复杂 |

### 当前为什么规则优先

工具名、参数、调用顺序、证据 ID、是否超时、是否泄露固定隐私值都有确定答案。交给 LLM 只会增加随机性。

### 不用 LLM Judge 行不行

当前 10 个指标可以完全不用，它们验证的是结构和明确约束。但回答是否自然、解释是否完整、医学表述是否准确等开放语义，最终需要专家或校准后的 Judge。

### LLM Judge 的常见偏差

- 位置偏差；
- 长答案偏好；
- 文风偏好；
- 自家模型偏好；
- Prompt 敏感；
- 多次评测不一致；
- 专业事实判断错误。

### 如何让 Judge 更可信

固定 Rubric、给参考答案和证据、隐藏模型身份、随机交换顺序、低温重复、多模型交叉、人工黄金集校准、计算一致率/Kappa、分歧和 S0/S1 人工复核。

## 21. 为什么评测数据集必须版本不可变

### 不可变解决什么

如果同一版本标准答案可以被直接修改，就无法判断分数变化来自 Agent 还是评测标准。

### 当前方案

- Dataset：逻辑集合；
- DatasetVersion：不可变快照；
- Case 内容规范化后计算 checksum；
- 相同内容重复导入幂等；
- 修改标签创建新版本；
- Run 固定引用一个版本。

### 不用行不行

一次性手工测试可以不用；只要需要版本对比、回归、审计或多人协作，就应该版本化。

### 与 Git 文件版本比较

JSONL 放 Git 也能版本化，但数据库版本便于 API 查询、Run 外键、权限和在线管理。最佳实践可以两者结合：Git 管评测定义的代码审查，数据库管执行快照和结果。

### 数据泄漏怎么避免

按来源、实体、时间或场景切分；测试集不参与 Prompt、阈值和权重调参；保留盲测；记录数据来源；合成数据人工抽检；定期做近重复检测。

## 22. 为什么需要 Adapter

### Adapter 解决什么

本地 Agent、HTTP 服务和固定回放输出格式不同。如果评测器直接依赖某个 Agent 内部对象，就无法跨版本复用。

当前通过 Adapter 统一为 `AgentOutput`：intent、slots、tool_calls、content、evidence_ids、fallback、error、trace。

### 不用行不行

只评一个固定服务时可以直接调用。但一旦要比较本地分支、测试环境、线上候选版本或离线 Fixture，Adapter 会显著降低耦合。

### Replay 为什么有价值

- 不需要模型 Key；
- 结果确定；
- CI 稳定；
- 可以验证“评测器能否识别已知错误”。

### Replay 的边界

它不能证明真实 Agent 效果，不能证明模型修复，不能覆盖真实网络和模型随机性。当前 `0/12 → 12/12` 只能讲成闭环演示。

### 与 Mock 的区别

Replay 是一种确定性测试替身，重放预先定义输出；Mock 通常还验证调用交互。面试中不要把 Replay 结果当真实线上数据。

---

## 23. 为什么 Trace 不能只记录最终答案

### 最终答案的问题

同一个错误答案可能来自不同环节：意图错、槽位丢、记忆污染、检索漏召回、工具参数错、工具超时、生成忽略证据或 Guardrail 漏拦截。没有 Trace 只能猜。

### 当前 Trace 事件

```text
user_message / intent_predicted / slot_extracted / retrieval / llm_call
tool_call / tool_result / guardrail / fallback / final_response / error
```

### 为什么 Trace 不是思维链

需要记录的是可观察业务事件、输入输出摘要、状态和耗时，不是模型隐式推理。保存思维链既不稳定，也有隐私和安全风险。

### 不用行不行

简单单模型问答可以只保留请求响应；涉及多轮、工具和高风险安全时，没有 Trace 很难闭环。

### OpenTelemetry 与自定义 Trace

- 自定义 Trace：快速贴合业务事件；
- OpenTelemetry：跨服务 trace/span、标准生态、后端可替换；
- 生产上可把业务事件作为 OTel span event，而不是二选一。

### 隐私取舍

不能“为了排障全量保存”。要脱敏 payload、Hash 用户标识、敏感原文加密分区、RBAC、保留期限、访问审计和删除机制。

### 定位原则

寻找关键信息第一次丢失的位置，而不是直接把锅甩给最后一个模块。

## 24. 为什么医疗安全采用硬门禁，不只看加权平均

### 加权平均的问题

95 条普通用例通过、5 条致命用例失败，平均仍是 95%。这不代表可以上线。

### 当前方案

- 隐私泄露为 S0；
- 禁止内容可标 S0/S1；
- S0/S1 触发 `hard_gate_failed`；
- 发布门禁要求 hard gate failure 为 0；
- 同时检查完成率、通过率、错误率和 P95。

### 不用硬门禁行不行

低风险娱乐应用可以只看整体分；医疗、金融、支付、隐私等高风险场景必须单独治理严重问题。

### 与风险加权比较

风险加权适合排序优化优先级，但不适合替代一票否决。推荐“硬门禁 + 分层指标 + 加权体验分”三层结构。

### 硬门禁也有问题

- 标签错误会误阻断发布；
- 小样本无法代表真实风险；
- 规则过严导致业务无法迭代。

因此 S0/S1 标签必须专家评审、双人标注和版本化，失败要人工复核。

## 25. 为什么需要 Badcase，而不是只看报表

### 报表只能回答“有多少错”

Badcase 闭环要回答：哪条错、错在哪一层、严重度、证据、负责人、修复方案、候选版本是否通过、有没有新回归。

### 当前闭环

```text
失败结果
→ 自动按首要失败维度分类
→ 关联 Case、Run、Trace 和 Metric evidence
→ triage 严重度和 owner
→ 修复
→ candidate run
→ 同一不可变 case 验证
→ baseline/candidate compare
→ 无新增 regression 才关闭
```

### 不用自动分类行不行

小规模可以人工整理 Excel；数量增加后，自动归因能提高效率，但最终责任阶段仍可能需要人工确认。

### 为什么“修复一条通过”还不够

可能过拟合单用例或引入其他回归，所以既跑专项 case，也跑全量版本比较。

## 26. 为什么需要 P50/P95，不只看平均延迟

平均值会掩盖长尾。九个请求很快、一个请求极慢，平均可能仍可接受，但真实用户会遇到卡死。

- P50：典型用户体验；
- P95：大多数用户的长尾体验；
- P99：极端长尾；
- error/timeout：仅有延迟不足以描述失败。

### 当前项目

评测汇总计算 P50、P95、wall time、错误率和发布阈值，并暴露 Prometheus 文本格式指标。

### 不用 Prometheus 行不行

本地演示可以看日志和报告；生产持续监控需要时间序列指标系统。Prometheus 优势是拉取模型、标签、告警生态；替代包括云监控、OpenTelemetry Metrics、InfluxDB 等。

### 指标陷阱

- 测试环境和生产硬件不同；
- 样本太少时 P95 不稳定；
- 只测健康接口没有意义；
- 并发、数据量、缓存命中率必须记录；
- “9 个端点 4.355 秒”不能证明单请求 P95，也不能证明 RAG 质量。

## 27. 为什么需要重试、降级、熔断、超时和幂等

这五个概念不能混淆。

| 机制 | 解决什么 | 示例 |
|---|---|---|
| Timeout | 不无限等待 | Embedding 5 秒未返回即失败 |
| Retry | 单次暂时故障 | 网络抖动后指数退避重试 |
| Degrade | 保留较弱能力 | 重排失败回退 RRF；ES/Milvus 失败走本地词法 |
| Circuit Breaker | 持续故障时停止请求下游 | 连续失败后 Open，冷却后 Half-Open |
| Idempotency | 重试不产生重复副作用 | 文档入库按 hash/version 去重 |

### 为什么不能无限重试

持续故障时会增加下游压力和用户延迟，形成重试风暴。重试要有限次数、只针对可重试错误、指数退避加抖动，并受总 deadline 控制。

### 当前代码事实

- TaskGraph 节点有有限重试；
- MCP 返回结构化错误，只有网络、超时和 HTTP 5xx 等可重试错误才进入下一次尝试；
- Rerank、Embedding、Milvus、Elasticsearch 和图谱检索已接入通用 Closed/Open/Half-Open 熔断器；
- Reranker 远程失败可依次回退本地确定性重排和 RRF；
- 基础设施不可用可进入本地路径；
- 真实外部依赖故障注入、集中指标告警与容量验收仍未完成。

### 面试高分表达

> 当前 retry、degrade 和通用三态 circuit breaker 都已进入代码合同：Open 时快速降级，Half-Open 只允许探测，成功后恢复。接下来要在真实 Milvus、Elasticsearch、Neo4j、Embedding 与 Rerank 服务上做故障注入，并把熔断次数、降级时长和恢复时间接入集中监控；不能把单测状态机说成生产韧性已经验收。

## 28. 关键技术“能不能删”速查表

| 技术 | 能否删除 | 删除后最小替代 | 什么时候必须加回来 |
|---|---|---|---|
| Vue | 能 | 纯 HTML 或 Swagger | 需要完整产品交互 |
| FastAPI | 能 | Flask/Go/Spring | 不是必须，只看团队和需求 |
| Pydantic | 能 | 手写校验/JSON Schema | 数据契约复杂、错误频发 |
| PostgreSQL | 能 | SQLite | 多用户并发、共享生产数据 |
| Milvus | 能 | pgvector/FAISS/ES kNN | 向量规模与性能要求增长 |
| Elasticsearch | 能 | PG 全文/SQLite FTS | 精确关键词与规模需求增长 |
| Neo4j | 很能 | 无图路/关系库 | 多跳关系任务有可测收益 |
| Kafka | 很能 | 日志/DB Outbox | 消费者增多、需要重放和解耦 |
| RRF | 能 | 单路或分数加权 | 异构多路检索需要稳健融合 |
| Query Rewrite | 能 | 原问题检索 | 多轮指代和口语漏召回明显 |
| Rerank | 能 | RRF top-k | 首阶段噪声影响答案 |
| TaskGraph | 能 | 顺序 ReAct | 并行、依赖、恢复需求出现 |
| GraphMemory | 能 | LongTerm 向量召回 | 关系型记忆有稳定收益 |
| SSE | 能 | 轮询 | 用户需要实时 token/进度 |
| LLM Judge | 能 | 规则 + 人工 | 开放语义指标规模化 |
| Hard Gate | 高风险场景不能随便删 | 人工发布审批 | S0/S1 自动治理成熟后仍保留 |

这张表的核心不是“全部都能删”，而是训练你用约束而非技术崇拜做决策。

## 29. 腾讯面试官连续追问模拟

### 第一组：FastAPI

**问：为什么用 FastAPI？**  
答：AI 和评测都在 Python 生态，Pydantic 契约、Swagger 和流式支持能降低开发成本；瓶颈主要是 I/O。

**追问：Flask 不行吗？**  
答：能做 MVP，但请求契约、OpenAPI、依赖注入和异步流需要补更多工程能力。

**追问：Go 性能不是更好吗？**  
答：Go 在并发和资源效率上更强，但本项目主要等待模型和数据库；团队开发效率和 AI 生态更重要。若网关成为瓶颈，可拆出 Go 网关，不必整体重写。

**追问：你 async 接口里用了同步 SDK 怎么办？**  
答：会阻塞事件循环；原生 async 就 await，同步 I/O 放线程池，CPU 密集放进程池，长任务放任务队列，并压测 P95 和 event-loop lag。

### 第二组：RAG

**问：为什么三路检索？**  
答：向量负责语义，BM25 负责精确词项，图谱负责关系；是否保留图路必须用关系型测试集证明。

**追问：三路一定比一路好吗？**  
答：不一定。路线会带来噪声、延迟和运维成本，必须做消融，按查询类型分析增益。

**追问：RRF 为什么好？**  
答：异构分数不可比时，按排名融合无需训练和分数校准，简单稳健。

**追问：RRF 有什么问题？**  
答：丢失原始分差、固定权重、不救候选漏召回，且分数不能当相关概率。

**追问：项目中图谱什么时候参与？**  
答：当前是 Hybrid 模式且图服务可用就参与，不是意图触发；理想方案是关系意图和实体置信度路由。

**追问：怎么证明父子分块有效？**  
答：和大块、小块做对照，比较 Recall@K、Context Precision、Faithfulness、token、索引体积和 P95。

### 第三组：Agent

**问：为什么不全部使用 ReAct？**  
答：简单任务会增加无意义规划、成本和误调用；先路由到确定性短路径，只让复杂任务进入 ReAct。

**追问：为什么自己写 TaskGraph，不用 LangGraph？**  
答：为了理解和控制依赖、并发、快照及与原逻辑对齐；但生产可靠执行上成熟框架更省成本，当前线程实现不等价于 durable workflow。

**追问：race group 有什么风险？**  
答：第一成功不代表其他调用真正取消，有副作用的 loser 可能仍执行；race 只适合幂等或只读操作，并需要底层取消传播。

### 第四组：评测

**问：为什么不用 BLEU/ROUGE？**  
答：开放问答存在多个正确表达，字面重叠不能充分代表事实和安全；本项目更关注意图、槽位、工具、证据、兜底和边界。文本质量再交给校准 Judge 或人工。

**问：为什么不能只看最终答案？**  
答：同一错误可能来自不同环节，Trace 才能找到关键信息第一次丢失的位置。

**问：LLM Judge 有什么偏差？**  
答：位置、篇幅、风格、自我偏好、Prompt 敏感和随机；用黄金集、交换顺序、重复、多模型、Kappa 和人工复核校准。

**问：95% 通过率为什么不能上线？**  
答：如果 5% 是漏急救、禁忌用药或隐私泄露，平均分没有意义；S0/S1 必须硬门禁。

**问：Replay 12/12 能证明修复吗？**  
答：只能证明评测器与闭环按预期工作，不能证明真实模型效果；真实结论要来自固定数据集上的实际 Local/HTTP Agent Run。

### 第五组：故障与数据

**问：Milvus 和 ES 都挂了，为什么还能用？**  
答：SQLite 保存 chunk，当前使用本地词法余弦检索；能保基础能力，但损失语义、BM25、图路和规模性能。

**追问：接口返回 200 就算降级成功吗？**  
答：不算。要验证质量、延迟、状态标识、租户隔离、恢复切回和索引一致性。

**问：为什么 Kafka 挂了不能影响聊天？**  
答：事件发布是旁路能力，主链应该隔离故障；但日志回退不等于可靠送达，生产要 Outbox 和幂等消费。

## 30. 你必须会做的三组消融实验

### 30.1 检索路线消融

```text
A：BM25
B：Vector
C：BM25 + Vector + RRF
D：BM25 + Vector + KG + RRF
E：D + Query Rewrite
F：E + Rerank
```

指标：Recall@5、MRR、nDCG@5、Evidence F1、P95、单次成本。  
切片：精确实体、同义表达、多跳关系、多轮指代、无答案。

结论不能只看总分。例如 KG 可能只在多跳切片提升，但让普通问题变慢。

### 30.2 分块消融

```text
A：800 大块直接召回
B：200 小块直接给模型
C：200 子块召回 + 800 父段落补全
D：语义分块
```

指标：Recall@K、Context Precision、Faithfulness、输入 token、索引体积、入库和查询 P95。

### 30.3 评测器一致性实验

```text
规则评测 vs LLM Judge vs 人工黄金标签
```

指标：准确率、Precision、Recall、F1、Cohen's Kappa、分歧率、成本和时延。  
高风险样本单独统计，不能被普通样本平均。

## 32. 最终回答原则

如果面试官问“为什么不用某方案”，不要贬低替代方案。高分回答通常是：

> 这个方案不是绝对最好，而是在当前数据规模、团队栈、交付时间和风险约束下更合适。小规模时我会选择更简单的方案；当指标证明出现瓶颈后再升级。当前实现解决了主问题，但我也能指出它引入的新复杂度以及下一步验证方式。

这句话体现的不是背诵能力，而是工程判断力。
