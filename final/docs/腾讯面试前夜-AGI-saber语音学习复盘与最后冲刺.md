## 2. 今天已经学清楚的内容

### 2.1 上传和入库不是同一件事

上传文档的前半段链路：

```text
前端上传
  → FastAPI 接收文件
  → 识别 JSON 文本或 multipart 文件
  → PDF / TXT / Markdown 解析
  → 文本清洗
  → 空文件与扫描 PDF 检查
  → 保存原文和文档版本
```

随后才进入 RAG Ingest：

```text
解析后的文本
  → 父块切分
  → 父块内部继续切子块
  → 子块批量 Embedding
  → 基础存储保存子块、父块、向量和版本关系
  → 子块原文写入 Elasticsearch
  → 子块向量写入 Milvus
  → 可选：后台抽实体关系写入 Neo4j
```

解析、Embedding 和索引写入目前包含同步操作，所以 Python 上传接口使用线程池执行，避免阻塞 FastAPI 的异步事件循环。否则一个长文档正在向量化时，聊天、健康检查和其他用户请求都可能被拖住。

### 2.2 Small-to-Big 父子分块

当前关系是：

```text
一个父块 → 多个子块
一个子块 → 一个父块
```

子块用于检索，父块用于补全上下文。

- 大块直接检索：主题过多，语义容易被稀释；
- 只返回小块：容易缺少前因后果；
- Small-to-Big：小块负责找得准，父块负责说得全。

当前 Python 源码不是维护一张独立的父块关系表，而是在保存子块时同时携带父块原文。检索命中子块后，可以直接取回父块内容。

### 2.3 一份子块如何写入多套存储

完整基础设施可用时：

- PostgreSQL：保存子块原文、父块原文、Embedding 和文档版本，是事实真相源；
- Elasticsearch：保存子块文本，提供 BM25 关键词检索；
- Milvus：保存子块向量，提供语义近邻检索；
- Neo4j：可选，保存实体与关系，用于多跳或关系型查询。

这些存储通过统一的块编号对齐。Milvus、Elasticsearch 和 Neo4j 都属于可重建索引；PostgreSQL 中的原始 Chunk 数据更接近真相源。

当可选基础设施缺失时，Python 产品模式可使用 SQLite 本地仓储。但当前源码核验到的本地路径主要是 SQLite 持久化和本地关键词评分，不能直接把它说成已经完整实现 SQLite Vector + FTS5 双路检索。

### 2.4 为什么同时使用向量和 BM25

向量检索擅长语义相似：

- “退款需要多长时间”可以匹配“退费处理周期”；
- 对同义改写和自然语言表达更稳。

BM25 擅长字面匹配：

- 项目编号；
- 专有名词；
- 报错码；
- 人名、药品名、政策条款等必须准确命中的内容。

不能说向量“完全做不到”关键词命中，更准确的说法是：向量不能稳定保证关键字面信号一定命中，因此需要 BM25 补充。

### 2.5 三路检索和两级 RRF

一条查询内部可以走三路：

1. Milvus 语义向量检索；
2. Elasticsearch BM25；
3. Neo4j 实体关系检索。

查询改写开启时，一个用户问题会变成多条等价查询。因此项目存在两层融合：

- 一级 RRF：一条查询内部，融合向量、BM25 和图谱结果；
- 二级 RRF：融合多条改写查询各自的检索结果。

RRF 的思路是按排名计分，不直接相加 Milvus 和 BM25 的原始分数：

```text
score(d) = Σ weight_i / (k + rank_i(d))
```

原因是余弦相似度和 BM25 分数不在同一量纲，直接相加不稳定。

当前 Go `845e8f7` 与 Python 的实际计分口径是：

- Milvus 语义路：`1.0`；
- Elasticsearch 关键词路：`1.0`；
- 知识图谱路：`kg_weight`；
- RRF 平滑常数：60；
- `semantic_weight=0.7`：仅为配置结构兼容保留，当前不参与 RRF。

专项结果必须以同一提交重新运行后的命令输出为准，静态文档不固化会随用例增长而过期的通过数。

平滑常数越小，单路头部名次优势越大；平滑常数越大，多路共同命中的价值更明显。60 是工程初始值，不是理论最优值，仍需要验证集调参。

### 2.6 RRF 和 Rerank 的分工

RRF 是粗排：

- 快；
- 不理解问题与段落之间的细粒度语义；
- 目标是形成覆盖面较大的候选池。

Rerank 是精排：

- 同时阅读“问题 + 候选段落”；
- 给候选打 0～10 分；
- 重新排序后截取最终 Top K。

当前 Go 和 Python 主版本都实现的是 **LLM Listwise Reranker**。如果模型超时、返回非法 JSON 或无法解析分数，则回退到 RRF 原顺序。

### 2.7 一次 RAG 查询中哪些地方使用模型

```text
用户问题
  → LLM 查询改写
  → 每条查询调用 Embedding 模型
  → Milvus / BM25 检索（非 LLM）
  → 可选：LLM 抽取查询实体后走 Neo4j
  → RRF（纯公式）
  → LLM Rerank
  → 阈值与去重（规则或相似度算法）
  → LLM 生成最终答案
```

不是所有环节都用聊天大模型：

- 语言理解使用模型；
- 数据库检索、RRF、阈值和去重应尽量使用确定性程序；
- 通过路由、缓存、降级和本地模型控制延迟与成本。

### 2.8 已核验的真实 RAG 评测数据

Go 仓库中真实存在：

- `test/test.txt`：10,000 条真实 Chunk；
- `test/gold.txt`：50 条 Golden Query；
- `test/generate_real_rag_dataset.py`：数据集构建脚本。

每条 Golden Query 包含：

- question；
- 5 个 ground truth Chunk ID；
- 3 / 2 / 1 的分级相关性；
- 来源文章、URL 和分类。

这支持以下指标：

- Recall@K：前 K 名找回了多少标准相关 Chunk；
- MRR@K：第一个相关 Chunk 排得是否靠前；
- NDCG@K：多个相关 Chunk 是否按强相关优先排列。

需要注意：

```text
至少命中一个 Gold → Hit@K
命中 Gold 数量 / Gold 总数 → Recall@K
```

语雀中有些例子把 Hit@K 和 Recall@K 混在了一起，面试时必须主动区分。

## 3. 当前发现的简历与源码差异

| 简历表述 | 当前源码核验 | 面试口径 |
|---|---|---|
| RRF 0.65 / 0.35 | 与源码不符；Milvus/ES 各为 1.0，KG 读取 `kg_weight` | 必须按实际计分讲；`semantic_weight=0.7` 只是兼容字段 |

| 0.30 无答案阈值 | Python 主链已执行门禁，但只接受有效远程 Rerank 分数 | 可以讲已实现；必须说明默认值仍需真实标注集校准 |
| 0.85 父片段去重 | 当前已做精确去重和 0.85 字符 3-gram/编辑相似度近重复去重 | 可以讲词法近似；不能说成 Embedding 语义余弦 |
| SQLite Vector + FTS5 | 当前本地仓储保存向量并做本地关键词评分，但未核到完整 FTS5 + Vector 查询 | 暂不说成完整双路降级 |
| Neo4j 权重 0.3 | 融合公式已经读取配置 | 可讲已接入；质量增益仍需消融验证 |

不要试图用背稿掩盖差异。最稳的原则是：

- 代码完成：讲实现、异常和测试；
- 文档设计：讲为什么这样设计；
- 尚未闭环：讲当前限制和下一步验证方式。

## 7. 明天面试的底线口径

不要说：

> 这些功能全部是我从零独立原创的。

可以说：

> 这个项目原本有 Go 版本和完整设计文档，我重点完成并验证了 Python/FastAPI 对齐版本，深入了 RAG、Agent Runtime 和评测链路，也在对照源码时发现并修正了配置不一致和部分能力未闭环的问题。

不要说：

> 图谱一定提升了检索效果。

可以说：

> 图谱主要补关系型和多跳问题，但当前公开 Benchmark 没有单独验证图谱增益，因此我不会报提升百分比，后续需要增加图谱消融集。

不要说：

> 单元测试全通过证明 RAG 效果很好。

可以说：

> 单元测试证明功能和契约稳定；RAG 效果必须用 Golden Query、召回和排序指标单独验证。

不要说：

> 整体通过率 95% 就能上线。

可以说：

> 医疗场景需要风险分层，致命和高风险问题设置硬门禁，不能被大量普通问题的平均分稀释。
